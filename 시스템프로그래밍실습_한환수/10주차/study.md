                                │
            ┌───────────────────┴───────────────────┐
            │                                       │
         CLIENT                                   SERVER
     서비스를 요청하는 쪽                     연결 요청을 기다리는 쪽
            │                                       │
         socket()                                socket()
            │                                       │

            │                                       │
         connect() ────── TCP 연결 요청 ──────────▶ accept()
            │                                       │
       client의 FD                            새로운 conn_fd
            │                                       │

LAB에서 바꾸는 부분

터미널에서 입력한 내용을 그대로 돌려주는 Echo

서버는 `listen_fd`로 접속을 받고 `conn_fd`로 특정 클라이언트의 데이터를 읽는다. 클라이언트는 보통 `socket → connect → read/write`, 서버는 `socket → bind → listen → accept → read/write` 순서다. 연결이 만들어진 다음에는 양쪽 모두 읽고 쓸 수 있다. 서버라는 이름 때문에 수신만 가능하고 클라이언트는 송신만 가능하다고 이해하면 안 된다.

## 3. IP·Port·Socket pair

### IP와 Port를 구분한다

IP는 통신 상대 호스트·인터페이스를 지정하고, Port는 그 호스트에서 어떤 서비스의 통신 끝점으로 전달할지 구분한다. 같은 서버 컴퓨터에서 웹 서버와 Echo 서버를 함께 실행할 수 있고, 각각 다른 포트로 접속한다. PDF 6페이지는 같은 IP의 80번 포트와 7번 포트가 다른 서비스로 연결되는 모습을 보여준다.

포트는 16비트 값이라 표현 범위는 0~65535다. PID는 프로세스 식별 번호이고, FD는 프로세스 안에서 열린 I/O 대상을 가리키는 번호다. 세 가지를 구분해야 한다. 포트가 1398이라고 Socket FD가 1398인 것은 아니고, Socket FD가 4라고 서버의 PID가 4인 것도 아니다.

| 이름 | 역할 | 교안의 예 |
| --- | --- | --- |
| 서버 IP | 접속할 서버 호스트 | `208.216.181.15` |
| 서버 Port | 접속할 서비스 | HTTP 예시 `80` |
| 클라이언트 IP | 접속을 요청한 호스트 | `128.2.194.242` |
| 클라이언트 임시 Port | 커널이 배정할 수 있는 로컬 Port | `51213` |

### Well-known port와 Ephemeral port

서버는 클라이언트가 찾아올 수 있도록 약속한 Port를 사용한다. 교안의 서비스 예시는 FTP 21, SSH 22, Telnet 23, SMTP 25, HTTP 80이다. 이것이 이번 실습에서 그 번호를 사용하라는 지시는 아니다. 실행 화면의 서버는 1398을 사용한다. 서버와 클라이언트가 동일한 목적지 Port에 맞추면 된다.

클라이언트는 보통 자신의 Port를 직접 고정하지 않는다. 목적지 IP와 Port를 설정하고 `connect()`하면 커널이 적절한 출발 주소와 임시 Port를 선택할 수 있다. 그래서 교안 Echo Client에 `bind()`가 없다. 클라이언트가 주소 없이 통신한다는 뜻이 아니라, 로컬 주소 선택을 OS에 맡기는 것이다.

### Socket pair

TCP 연결은 양 끝 주소를 함께 보아 구분한다.

```text
(클라이언트 IP, 클라이언트 Port, 서버 IP, 서버 Port)

예시
(128.2.194.242, 51213, 208.216.181.15, 80)
```

서버 Port가 같아도 클라이언트 주소가 달라 서로 다른 연결을 구분할 수 있다. 여러 연결을 구별할 수 있다는 것과 애플리케이션이 여러 연결을 동시에 처리한다는 것은 별개다. 이번 Echo Server는 한 연결을 처리하는 동안 안쪽 read 반복문에 머무는 순차 구조다.

교안의 ‘Port가 프로세스를 식별한다’는 표현은 해당 서비스의 소켓으로 전달한다는 의미로 이해하면 된다. 프로세스가 항상 Port 하나만 사용하거나, Port와 PID가 일대일로 같은 번호를 갖는다는 뜻으로 확대하지 않는다.

## 4. 클라이언트·서버와 Socket FD

Client와 Server는 통신에서 맡은 역할이다. 같은 컴퓨터의 두 터미널에서 두 프로세스를 실행해도 되고, 서로 다른 컴퓨터에서 실행해도 된다. 서버는 요청을 기다리며 자원을 다루어 서비스를 제공하고, 클라이언트는 접속해 서비스를 요청한다. Echo에서는 받은 데이터를 되돌려주는 것이 서비스이고, 이번 Lab에서는 파일을 전달받아 저장하는 것이 서비스다.

서버도 ACK나 응답을 보내므로 양쪽 모두 읽고 쓸 수 있다. TCP 연결은 Full-duplex, 즉 양방향으로 통신할 수 있다. 파이프에서 읽기·쓰기 끝을 구분했던 경험을 그대로 ‘서버는 읽기만, 클라이언트는 쓰기만’으로 가져오면 안 된다.

커널에서 Socket은 통신의 끝점이고, 애플리케이션은 이를 정수 FD로 사용한다. `socket()`이 성공하면 반환된 FD를 보관하고 연결 준비 후 `read()`나 `write()`에 전달한다. 일반 파일을 `open()`한 뒤 FD로 다루던 방식과 연결된다. 달라지는 핵심은 데이터를 주고받기 전에 소켓과 연결을 어떻게 준비하느냐다.

```text
일반 파일                        연결된 TCP 소켓

open("Aladdin", ...)             socket(...) + connect(...)
        ↓                                  ↓
      file_fd                           socket_fd
        ↓                                  ↓
    read/write                          read/write
        ↓                                  ↓
      close                               close
```

파일 전송 클라이언트에는 로컬 파일을 읽는 파일 FD와 서버로 보내는 Socket FD가 함께 등장한다. 서버에는 클라이언트 연결 FD와 `_copy` 파일을 쓰는 파일 FD가 등장한다. 각 `read/write`의 첫 인자를 따라가면 ‘어디에서 읽어 어디로 보내는가’를 구분할 수 있다.

PDF 10페이지는 사용자 프로그램, Socket 시스템콜, 커널 TCP/IP, 네트워크 어댑터의 계층을 보여준다. 사용자가 `write()`를 호출한다고 직접 네트워크 카드의 레지스터를 다루는 것이 아니다. OS가 제공하는 인터페이스를 통해 통신 기능을 사용하는 것이다.

PDF는 오래 실행되며 요청을 기다리는 서버를 daemon과 연결해 설명한다. 이번 Lab에 부팅 시 자동 실행이나 daemon화까지 구현하라는 지시는 없다. 터미널에서 실행해 연결을 기다리는 서버의 동작을 이해하면 된다.

## 5. TCP와 UDP

| 구분 | TCP | UDP |
| --- | --- | --- |
| 교안 핵심 | 연결 지향, 신뢰성 있는 바이트 스트림 | 연결 없는 데이터그램 |
| 데이터 관점 | 순서가 있는 연속 바이트 | 개별 데이터그램 |
| 서버 예시 흐름 | socket → bind → listen → accept | socket → bind → recvfrom |
| 클라이언트 예시 흐름 | socket → connect | socket → 주소 준비 → sendto |
| 송수신 예시 | read/write | recvfrom/sendto |
| 이번 Lab과 연결 | TCP Echo 코드를 파일 전송으로 확장 | 비교용 설명 |

TCP가 신뢰성을 제공한다는 것은 순서·재전송 등을 전송 계층에서 처리한다는 의미다. 파일명과 본문을 자동으로 구별해준다는 의미는 아니다. TCP는 바이트 스트림이므로 송신자가 `write()` 두 번을 했다고 수신자에게 `read()` 두 번으로 정확히 대응하지 않는다. 한 번에 합쳐 받거나, 여러 번에 나눠 받을 수 있다.

UDP를 ‘빠르다’고 소개한 문장을 모든 환경에서 반드시 TCP보다 빠르다고 해석하지 않는다. 또 TCP라고 해서 프로그램의 잘못된 버퍼 처리나 잘못된 파일 길이까지 해결되는 것도 아니다. 이번 주는 연결을 만드는 순서와 연결 위에서 바이트를 주고받는 흐름을 우선 공부한다. UDP 서버·클라이언트를 함께 제출하라는 요구는 PDF에 없다.

## 6. 주소 구조체와 바이트 순서

### sockaddr와 sockaddr_in

`bind/connect/accept`는 여러 주소 계열에 공통으로 사용하는 `struct sockaddr *` 인터페이스를 받는다. IPv4 주소는 구체적인 필드가 있는 `struct sockaddr_in`으로 준비한다. 호출 때 `(struct sockaddr *)&addr`처럼 포인터 형식을 맞추는 이유다.

| 필드 | 저장 내용 | 예제 |
| --- | --- | --- |
| `sin_family` | 주소 계열 | IPv4는 `AF_INET` |
| `sin_port` | 네트워크 바이트 순서의 Port | `htons(port)` |
| `sin_addr` | IPv4 주소 | 목적지 IP 또는 로컬 바인드 주소 |
| `sin_zero` | 패딩 | 전체 구조체 초기화 시 0으로 설정 |

```c
/* 교안의 주소 준비 형태를 설명하는 부분 코드 */
memset(&addr, 0, sizeof(addr));
addr.sin_family = AF_INET;
addr.sin_port = htons(port);
```

이 부분만으로 완성된 클라이언트나 서버가 되는 것은 아니다. 어떤 IP를 넣는지와 `connect()` 또는 `bind()` 중 어디에 넘기는지까지 봐야 한다. 클라이언트 주소 구조체는 접속할 서버의 주소를 담고, 서버의 바인드용 구조체는 연결을 받을 로컬 주소를 담는다.

### memset과 memcpy

20페이지는 두 함수의 매뉴얼 화면이다. `memset`은 정해진 바이트 값으로 메모리 구간을 채운다. 교안은 구조체 전체를 0으로 초기화한다. `memcpy`는 지정한 바이트 수의 메모리를 복사하며, Echo Client는 호스트 조회로 얻은 IP 주소 데이터를 주소 구조체로 복사한다.

문자열의 널문자를 기준으로 복사하는 함수가 아니라 크기를 지정해 메모리를 다룬다는 점이 중요하다. IP 주소의 이진 표현과 `127.0.0.1`처럼 사람이 읽는 문자열 표현도 구분한다. 어떤 데이터를 어떤 크기로 복사하는지 확인한다.

### htons와 htonl

`htons`는 Host to Network Short, `htonl`은 Host to Network Long의 약자다. 서로 다른 장치가 숫자를 같은 규칙으로 해석하도록 네트워크 바이트 순서로 바꾼다. 교안에서는 Port에 `htons()`, 서버의 `INADDR_ANY`에 `htonl()`을 적용한다. 바이트 순서 변환은 서버 조회나 접속과 별개다.

### INADDR_ANY와 localhost

서버의 `INADDR_ANY`는 특정 로컬 IPv4 주소 하나에만 제한하지 않고 로컬 인터페이스들을 대상으로 연결을 받을 때 사용한다. 클라이언트 목적지에 무조건 `0.0.0.0`을 쓰라는 의미는 아니다. 같은 컴퓨터에서 실습하면 클라이언트는 교안처럼 `localhost`를 사용해 서버 Port로 접속할 수 있다.

## 7. 소켓 API와 연결 순서

| API | 하는 일 | 중요한 결과 |
| --- | --- | --- |
| `socket(domain, type, protocol)` | 소켓 생성 | 성공하면 FD, 실패하면 -1 |
| `connect(fd, addr, len)` | 상대 주소로 접속 | 예제에서는 TCP 서버에 연결 |
| `bind(fd, addr, len)` | 로컬 주소·Port 배정 | 서버의 수신 주소 준비 |
| `listen(fd, backlog)` | 연결을 기다리는 수동 소켓으로 전환 | 아직 파일 내용을 읽는 단계는 아님 |
| `accept(listen_fd, addr, addrlen)` | 대기 중 연결을 받아들임 | 별도의 연결 FD 반환 |
| `read(fd, buf, count)` | 바이트 수신 | 실제 읽은 수, EOF, 오류 구분 |
| `write(fd, buf, count)` | 바이트 쓰기 | 실제 쓴 바이트 수 확인 |
| `close(fd)` | FD 닫기 | 연결별 수명과 서버 전체 수명 구분 |

`socket(AF_INET, SOCK_STREAM, IPPROTO_TCP)`는 교안의 IPv4 TCP 생성 조합이다. `AF_INET6`는 IPv6이고 `AF_UNIX`는 로컬 Unix domain 주소 계열이다. Socket API를 쓴다고 모든 통신이 반드시 외부 인터넷을 경유하는 것은 아니다.

`backlog`는 커널에서 대기시킬 연결 Queue와 관련된 인자다. 파일 전송 버퍼 크기나 서버가 이미 받아들인 전체 연결 수와 같은 뜻이 아니다. 예제의 `listen(fd, 5)`에서 5가 TCP 전체의 고정 연결 제한이라고 외우지 않는다.

`accept()`는 상대 주소를 출력 인자로 받을 수 있다. 그래서 `socklen_t conn_addr_len`을 구조체 크기로 초기화하고 그 주소를 넘긴다. 주소 길이를 값으로 전달하는 `bind/connect`와 길이 변수의 포인터를 전달하는 `accept`를 코드에서 구분한다. `accept()`의 성공 반환값은 IP나 Port가 아니라 새 연결용 FD다.

교안의 기본 소켓은 Blocking 흐름으로 설명한다. 데이터가 아직 없거나 접속이 아직 없을 때 함수가 기다릴 수 있다. 화면에 아무 로그가 안 나온다고 곧바로 프로그램이 잘못되었다고 판단하기보다, 현재 어느 함수가 무엇을 기다리고 있는지 먼저 확인한다.

## 8. listen_fd와 conn_fd

```text
서버

listen_fd = socket(...)
bind(listen_fd, ...)
listen(listen_fd, ...)
          │
          ├─ accept(listen_fd, ...) → conn_fd_A
          │                           │
          │                         A와 read/write
          │                           │
          │                         close(conn_fd_A)
          │
          └─ accept(listen_fd, ...) → conn_fd_B
                                      │
                                    B와 read/write
```

Listening FD는 새 접속을 받는 창구다. 서버가 계속 운영되면 유지한다. Connected FD는 받아들인 특정 클라이언트와 데이터를 주고받는 연결이다. 새 연결을 `accept`할 때마다 연결용 FD를 받는다. 코드에서 같은 변수명을 반복 사용하더라도 이전 연결과 새 연결은 별개다.

서버가 `read(listen_fd, ...)`로 클라이언트 파일을 받으려 하면 역할이 맞지 않는다. 데이터를 읽을 대상은 `accept()`가 반환한 연결 FD다. 반대로 클라이언트 하나의 처리가 끝났다고 Listening FD까지 닫으면 다음 연결을 받을 창구를 없애게 된다.

클라이언트에서 `connect()`한 Socket FD와 서버에서 `accept()`한 Connected FD가 연결된 양 끝이다. 각각의 프로세스가 관리하는 로컬 정수 번호이므로 양쪽 FD 숫자가 같을 필요는 없다. 포트와 FD를 같은 개념으로 해석하지 않는 연습이 필요하다.

18페이지는 `connect/accept`의 대응을 입문용 흐름으로 보여준다. 이 그림을 TCP 연결 완료와 서버 애플리케이션의 `accept` 반환 시점이 항상 정확히 같은 순간이라는 보장으로 확대하지 않는다. 이번에는 각 호출의 역할과 연결 뒤 FD 관계를 중심으로 읽는다.

## 9. Echo Client 코드 흐름

21~22페이지 클라이언트의 순서는 다음과 같다.

1. 인자를 검사해 호스트와 Port를 받는다. 예시는 `./client localhost 1398`이다.
2. Port 문자열을 `strtol()`로 정수로 바꾸고 범위를 검사한다.
3. `socket()`으로 IPv4 TCP 소켓을 만든다.
4. `gethostbyname(host)`로 호스트 주소를 구한다.
5. 주소 구조체를 초기화하고 서버 IP·Port를 설정한다.
6. `connect()`로 서버에 접속한다.
7. 표준입력에서 읽어 서버에 보내고, Echo 응답을 읽어 표준출력에 쓴다.
8. 입력이 끝나면 소켓을 닫는다.

```text
키보드 입력
   ↓ read(STDIN_FILENO, ...)
Client 버퍼
   ↓ write(conn_fd, ...)
Server 연결 소켓
   ↓ Echo 응답
Client 버퍼
   ↓ write(STDOUT_FILENO, ...)
화면 출력
```

`read(STDIN_FILENO, ...)`와 `read(conn_fd, ...)`는 함수가 같지만 입력 원천이 다르다. 하나는 키보드 등 표준입력이고 하나는 서버가 보낸 데이터다. 변수 `n`을 재사용하므로 현재 어느 `read()`의 반환값이 들어 있는지 코드 순서대로 확인한다.

`MAXLINE`은 이 예제에서 80이다. 이는 한 번 읽는 버퍼 크기이며 연결 전체에서 최대 80바이트만 보낼 수 있다는 뜻은 아니다. 더 큰 데이터는 반복해서 읽고 쓰면 된다. 큰 파일을 다룰 때 무조건 파일 크기만큼 버퍼를 잡는 방식만 가능한 것이 아니다.

26페이지에는 영문·한글·이모지를 입력해 Echo를 확인하는 터미널 화면이 있다. 서버의 `got ... bytes`는 받은 바이트 수다. UTF-8에서 문자 하나는 여러 바이트일 수 있고 줄바꿈도 포함되므로 눈에 보이는 글자 수와 같다고 가정하지 않는다.

## 10. Echo Server 코드 흐름

23~25페이지 서버는 초기화 이후 두 겹 반복문으로 구성된다.

```text
인자 검사 → socket → 주소 준비 → bind → listen
                                        │
                                        ▼
바깥 반복문: 새 클라이언트 연결을 계속 받는다
  accept()
      │
      ▼
  안쪽 반복문: 현재 연결에서 오는 바이트를 Echo한다
    read(conn_fd)
        ↓
    write(conn_fd)
        ↓
    다시 read(conn_fd)
      │
      └─ EOF 또는 오류 → 안쪽 반복문 종료
                            ↓
                       close(conn_fd)
                            ↓
                       다음 accept()
```

`socket/bind/listen`을 매번 다시 수행하는 구조가 아니라 먼저 서버를 준비한 뒤 `accept`를 반복한다. 현재 연결에서 받은 데이터를 돌려주다가 클라이언트가 송신을 끝내면 EOF를 확인하고 그 연결을 닫는다. 이후 다시 새로운 클라이언트 연결을 받을 수 있다.

교안 코드는 `accept()` 실패 시 메시지를 출력하고 다음 반복으로 넘어간다. `read()`의 반복 조건은 양수이므로 0과 음수에서 모두 반복문을 빠져나오지만, 정상 EOF와 읽기 오류의 의미는 다르다. 구현 검토에서는 두 경우를 구분하는 것이 좋다.

이 예제에는 동시 처리를 위한 `fork()`나 Thread 생성이 없다. 현재 클라이언트가 연결을 유지한 채 데이터를 보내지 않으면 서버가 그 연결의 `read()`에서 기다릴 수 있다. 동시에 여러 연결을 처리하는 서버는 별도 확장이다. PDF는 동시 서버를 이번 Lab 필수 요구로 지정하지 않았다.

## 12. 파일 전송 프로토콜 보충

**이 절은 구현 이해를 위한 보충이다. 특정 헤더·길이 필드·연결 재사용 방식을 교수님이 강제했다는 뜻은 아니다.** 30페이지의 ACK도 ‘Possible flow’로 제시한 힌트다.

### 파일명과 본문의 경계

Echo는 받은 바이트를 돌려주면 되지만 파일 전송은 메타데이터와 본문을 구분해야 한다. 파일명의 끝, 본문의 시작, 본문의 끝, 다음 파일의 시작을 양쪽이 같은 규칙으로 알아야 한다. 이러한 애플리케이션의 약속이 프로토콜이다.

```text
송신 의도
[파일명 Aladdin] [파일 내용 ...] [파일명 text] [파일 내용 ...]

TCP가 제공하는 것
순서가 있는 연속 바이트

수신자가 판단해야 하는 것
어디까지 파일명인가?
어디부터 본문인가?
이 파일은 언제 끝나는가?
다음 파일은 언제 시작하는가?
```

파일명 한 번 write, 본문 한 번 write만으로 경계가 자동 보존되지는 않는다. 첫 read에 파일명과 본문 일부가 함께 들어오거나 파일명이 쪼개질 수 있다. 시간차를 주기 위해 `sleep()`을 넣는 것도 데이터를 구분하는 약속을 대신할 수 없다. 로컬에서 우연히 동작하는 것과 프로토콜로 경계가 정의된 것은 다르다.

### ACK가 해결하는 것

교안 힌트는 파일명을 보내고 서버가 ACK를 돌려준 다음 클라이언트가 전송을 이어가는 흐름이다. 이는 ‘서버가 다음 단계를 준비했다’는 식으로 서로의 진행 단계를 맞추는 역할이다. TCP 내부의 전송 확인과 구분되는 애플리케이션 메시지다.

ACK 하나만으로 파일 본문의 끝까지 자동으로 알게 되는 것은 아니다. 파일명을 어떤 단위로 받고 ACK를 몇 바이트 읽는지, 본문의 길이를 어떻게 정하는지는 별도 규칙이 필요하다. 교수님의 추가 지시가 있으면 이를 우선하고, 본인이 고른 규칙은 서버와 클라이언트 양쪽에 일치시킨다.

### 본문의 끝과 프로그램 종료

파일 크기를 먼저 보내고 정확히 그 길이만큼 받는 방식은 연결을 유지하면서 여러 파일을 나누기 좋다. 파일 하나마다 연결을 사용하는 방식은 연결 수명과 다시 접속하는 흐름을 따로 정해야 한다. PDF에는 같은 TCP 연결 하나를 끝까지 재사용해야 한다는 명시적 요구는 없다.

한 연결을 유지하면서 매 파일을 ‘소켓 EOF가 올 때까지 읽기’로 처리하면 양쪽이 기다리게 될 수 있다. 클라이언트는 파일 전송을 마쳤다고 생각하고 다음 입력을 기다리는데 서버는 더 올 데이터를 기다리는 식이다. 파일 하나의 완료와 전체 프로그램 종료를 구분해야 한다.

특정 문자열을 파일 끝 표식으로 사용하려면 실제 본문에 그 문자열이 나타나는 경우도 고려해야 한다. 텍스트 파일이라는 조건만으로 모든 구분자 방식이 안전해지는 것은 아니다. 전송을 위해 원본 본문을 임의로 바꾸거나 끝에 널문자를 추가하지 않도록 유의한다.

### 상태 흐름으로 정리

```text
Client                           Server
파일명 입력                       파일명 대기
    ↓                                ↓
파일 열기/정보 준비                파일명 수신 및 준비
    ↓                                ↓
메타데이터 전송 ─────────────────▶ 메타데이터 해석
    ↓                                ↓
준비 응답 대기 ◀───────────────── 준비 응답
    ↓                                ↓
본문 전송 ───────────────────────▶ 본문 저장
    ↓                                ↓
파일 전송 완료                    파일 저장 완료
    ↓                                ↓
다음 입력/quit                    다음 파일/연결 종료 처리
```

이는 학습용 논리 구조이며 완성 제출 코드가 아니다. 각 단계에서 ‘누가 무엇을 몇 바이트 기다리고 있는가’와 ‘어떤 조건이면 다음 상태로 이동하는가’를 정리하면 구현 중 막히는 위치를 찾기 쉽다. 코드의 함수 이름만 보기보다 상태를 함께 적어본다.

## 13. 입출력·오류 처리 보충

### 실제 바이트 수로 판단

`read()`는 실제 읽은 바이트 수를 반환한다. 버퍼가 4096바이트라도 항상 4096바이트를 채운다고 보장하지 않는다. 작은 양수는 이번에 읽은 데이터 크기이고, 0은 EOF, -1은 오류다. 특히 Socket에서 짧게 읽었다는 사실만으로 파일 하나가 끝났다고 판단하면 안 된다.

프로토콜로 전체 파일 길이를 알고 있다면 지금까지 받은 바이트와 남은 바이트를 추적한다. ‘버퍼를 한 번 채웠는가’와 ‘총 길이를 모두 받았는가’는 다르다. 큰 파일을 작은 버퍼로 스트리밍할 때 필요한 기본 관점이다.

`write()`도 실제 반환값을 확인한다. n바이트를 요청했다고 언제나 n바이트를 썼다고 가정하면 안 된다. 일부만 썼다면 남은 구간을 이어서 쓰는 처리와 오류 처리를 고려한다. 서버가 결과 파일에 저장하는 write도 같은 관점이다. 교안 Echo 예제는 연결 흐름을 보여주기 위해 간결하게 작성되었으므로 파일 전송에 적용할 때 입출력을 보완할 수 있다.

### C 문자열과 파일 본문

`read()`는 끝에 `\0`을 자동 추가하지 않는다. 파일명을 문자열로 사용할 때는 실제 길이와 널 종료를 관리해야 한다. 반면 파일 본문은 읽은 바이트 수를 그대로 써야 한다. 본문마다 `strlen()`으로 길이를 다시 계산하거나 널문자까지 파일에 저장하면 원본과 달라질 수 있다.

파일명 50바이트 미만이라는 조건과 버퍼에 수신한 데이터를 전부 문자열처럼 다루는 것은 별개다. 입력 줄바꿈이 파일명에 포함되어 파일을 못 여는 경우도 구분한다. UTF-8 문자열에서는 문자 개수와 바이트 수가 같지 않을 수 있으므로 교안의 제한도 바이트 기준으로 읽는다.

### 대기와 실패 구분

| 증상 | 우선 점검 |
| --- | --- |
| bind 실패 | Port 사용 중인지, 로컬 주소가 맞는지 |
| connect 실패 | 서버 실행, 목적지 IP·Port, 네트워크 접근 |
| accept에서 대기 | 아직 접속이 없다면 정상 대기일 수 있음 |
| read에서 멈춤 | 상대의 현재 송신 단계, 본문 종료 경계 |
| 일부만 복사됨 | 부분 read/write, 누적 바이트 수, 중간 오류 |
| 파일에 이상한 내용 추가 | 실제 길이 대신 버퍼 전체를 썼는지 |
| 두 번째 파일부터 섞임 | 이전 파일 잔여 데이터와 다음 메타데이터 경계 |
| 재접속이 안 됨 | Listening FD를 닫았는지, 다음 accept로 돌아가는지 |

로그를 넣는다면 파일명 수신, 준비 응답, 본문 시작, 받은 바이트 수, 저장 완료, 연결 종료를 구분하면 좋다. 출력 문구보다 양쪽이 서로 무엇을 기다리는지를 비교한다. 이 표는 일반적인 디버깅 방향이며, 현재 사용자의 실습 코드에서 이 오류들이 발견되었다는 의미는 아니다.

## 14. 실행·검증·제출

### 실행 순서

한 터미널에서 서버를 먼저 실행하고 다른 터미널에서 클라이언트를 실행한다. 교안 예시 호출은 `./server 1398`, `./client localhost 1398`이다. 같은 머신에서 먼저 확인하면 원격 네트워크 문제와 코드 흐름 문제를 나누어 볼 수 있다. 파일 경로와 작업 디렉터리도 확인한다.

클라이언트가 읽는 원본과 서버가 쓰는 복사본이 같은 디렉터리에 있을 수도, 다른 디렉터리에 있을 수도 있다. 이름만 같은 다른 파일을 비교하지 않도록 원본 경로와 결과 경로를 명확히 한다. 서버가 파일을 만들었다는 사실만으로 내용 전체가 보존되었다고 단정하지 않는다.

| 확인 사례 | 확인할 결과 |
| --- | --- |
| 작은 파일 하나 | 원본과 `_copy` 내용 일치 |
| 버퍼보다 큰 파일 | 여러 번 읽고 써도 전체 내용 보존 |
| 파일 두 개 연속 | 내용이 섞이지 않고 결과 파일이 각각 생성 |
| 마지막 줄에 줄바꿈 없음 | 마지막 바이트 누락·추가 없음 |
| UTF-8 한글 포함 | 문자 수와 바이트 수를 혼동하지 않음 |
| quit 입력 | 입력 반복 종료와 Socket 정리 |
| 종료 후 재접속 | 서버가 다음 연결 처리 가능 |

파일 내용은 `cmp Aladdin Aladdin_copy` 또는 `diff -u Aladdin Aladdin_copy`로 비교할 수 있다. 크기는 `wc -c`나 `stat`로 확인한다. 크기가 같은 것은 필요한 확인 중 하나지만 내용까지 같다는 충분조건은 아니다. 실제 테스트 실행 결과와 단순한 체크리스트 작성 상태를 구분한다.

### 제출 구조

```text
week10/
├── Makefile
├── server.c     ← 실제 소스 분할은 본인 구현에 따름
└── client.c

make가 만들어야 할 실행파일
./server
./client

상위 디렉터리에서 압축
 tar caf 2024315329_w10.tar.zst week10
```

PDF의 필수 조건은 Source code·Makefile 제출과 `make`로 두 실행파일이 생성되는 것이다. 소스를 반드시 두 파일로만 작성하라고 제한한 것은 아니다. 공통 코드를 분리했다면 필요한 소스와 헤더가 압축본 안에 함께 있어야 한다. 기존 실행파일이 남아 있어서 우연히 동작하는 경우와 소스에서 정상 빌드되는 경우를 구분한다.

VMShare의 실제 작업물, 저장소의 주차 자료, PA2 연습 폴더를 이름만 보고 섞지 않는다. 실제 `week10`을 묶었는지 압축 내용을 확인한다. 기존 원본은 임의로 이동·덮어쓰기 하지 않고, 제출본을 보관할 때는 실제 압축 경로와 내용으로 확인한다. 정확한 제출 시각은 iCampus의 이번 주 제출 안내를 따른다.

## 15. 이전 IPC·RoverAid와 연결

| 이전 내용 | 이어지는 점 | 새로 구분할 점 |
| --- | --- | --- |
| Unix I/O | FD, 반복 read/write, 실제 바이트 수 | 디스크 파일 대신 네트워크 끝점 |
| Anonymous pipe | 바이트 흐름을 읽고 쓰는 모델 | IP·Port와 연결 준비가 추가됨 |
| Named pipe | 통신 끝점에 이름을 부여한다는 발상 | 파일 경로 대신 네트워크 주소로 상대 지정 |
| Message queue | 여러 데이터 단위를 주고받음 | TCP는 메시지 경계를 직접 정해야 함 |
| Process/fork | 서버도 실행 중인 프로세스 | 이번 순차 예제에 fork 동시 처리는 없음 |

RoverAid의 노트북–Raspberry Pi 통신도 Socket과 바이트 스트림이라는 기반 위에 있다. 길이 정보를 붙인 JSON 메시지는 TCP가 애플리케이션 메시지를 자동으로 나눠주지 않는 문제를 해결하는 한 방법이다. 이번에는 프로젝트에서 사용해본 통신을 C 시스템콜 수준으로 다시 이해하는 기회가 된다.

어느 장치가 서버인지는 설계에 따라 다르다. 노트북이라고 항상 클라이언트, Pi라고 항상 서버가 아니다. 접속을 기다리는 역할과 connect로 접속하는 역할을 기준으로 나눈다. 이번 Lab은 파일을 보내는 클라이언트와 파일을 받아 저장하는 서버라는 역할을 지정한 것이다.

## 16. 복습 체크포인트

### 개념 설명

1. IP·Port·FD·PID의 차이를 말할 수 있다.
2. 같은 서버 Port로 접속한 두 연결이 어떻게 구별되는지 설명한다.
3. 클라이언트에 bind가 없어도 로컬 주소가 생기는 이유를 안다.
4. socket·bind·listen·accept·connect의 역할을 각각 말한다.
5. listen_fd와 conn_fd의 수명과 read/write 대상을 구분한다.
6. sockaddr_in의 필드, htons/htonl, memset/memcpy의 용도를 안다.
7. Echo 서버의 두 반복문과 EOF 후 동작을 설명한다.
8. TCP의 신뢰성과 애플리케이션 파일 경계를 구분한다.
9. 파일명 ACK와 본문 종료 조건이 해결하는 문제가 다름을 안다.
10. 본문을 작은 버퍼로 여러 번 보내도 보존할 수 있는 이유를 설명한다.

### 제출 전 확인

- [ ] 반복 입력과 quit 종료가 구분된다.
- [ ] 확장자 없는 텍스트 파일을 원본 내용 그대로 전송한다.

- [ ] 버퍼보다 큰 파일과 연속된 파일 전송을 확인한다.

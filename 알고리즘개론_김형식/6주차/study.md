### B02. 전체 개념 지도

```text
이전 시간: 탐색
  비교만 사용 -> 결정 트리 -> 최악 Omega(log n)
  정수 key + random access -> 직접 접근 배열 -> O(1) 조회
  큰 key 공간 -> 공간 낭비 -> 해싱 -> 기대 시간 분석
                    |
                    v
이번 시간: 정렬
  비교만 사용
    -> 서로 다른 원소 n개의 가능한 순서 n!
    -> 결정 트리의 잎이 적어도 n!개
    -> 높이가 적어도 log2(n!)
    -> 최악 Omega(n log n)
                    |
                    v
비교 이외의 정보를 사용하면?
  정수 key를 배열 인덱스로 사용
    -> Direct Access Array Sort
    -> O(n + u), 단 key가 서로 달라야 함
                    |
                    v
key 범위가 커지면?
  K = a*n + b
    -> 작은 범위의 자릿수 여러 개
    -> 덜 중요한 자리부터 안정 정렬
                    |
                    v
자릿수는 중복될 수 있음
  -> key별 순서 보존 버킷
  -> stable Counting Sort, O(n + u)
                    |
                    v
Counting Sort로 자릿수를 반복 정렬
  -> Radix Sort
  -> base n, d개 자리일 때 O(n*d + n)
  -> 전체 key 범위가 n의 고정 차수 다항식이면 O(n)
```

이 강의에서 `n`은 정렬할 원소의 수, `u`는 정수 key 공간의 크기를 나타낸다. 일반적인 표기는 `0 <= key < u`로 통일한다. `u`는 최댓값 그 자체와 한 칸 차이 날 수 있지만, 배열 길이와 범위가 무엇인지 분명히 구분하면 된다. Radix Sort에서는 원래 정수의 범위와 한 자릿수의 범위가 다르다. 아래에서는 원래 범위를 `U`, 한 자리의 진법을 `b`라고 쓰기도 한다. 이는 혼동을 막기 위한 표기 보강이며 다른 알고리즘을 추가한 것이 아니다.

### B03. 0:32~2:55 비교 탐색과 직접 접근 배열

지난 탐색 강의의 출발점은 comparison model이다. 저장된 두 객체를 비교해서 같은지, 작은지 등의 제한된 정보를 얻는다. 한 번의 비교가 상수 개의 결과로만 갈라진다면 그 과정을 결정 트리로 나타낼 수 있다. 가능한 탐색 결과가 `n`개 정도라면, 상수 분기 트리의 높이는 적어도 로그 규모여야 한다. 따라서 이 모델의 일반 탐색은 최악의 경우 `Omega(log n)`의 비교를 요구한다.

그러나 이 결론은 모든 계산 모델에 대한 절대적인 금지가 아니다. 강의에서 쓰는 컴퓨터는 random access라는 더 강한 연산을 지원한다. 이미 알고 있는 배열 인덱스의 위치로 곧바로 접근할 수 있다. 정수 key가 `K`인 객체를 배열의 `K`번 칸에 놓기로 약속하면, 비교를 여러 번 하는 대신 `A[K]`를 바로 확인할 수 있다. 이 약속이 direct access array, 즉 직접 접근 배열의 핵심이다.

```text
일반적인 sequence 배열
  index 0 -> 어떤 원소든 저장 가능
  원소의 위치는 사용자가 정한 순서의 일부

직접 접근 배열
  index K -> key가 K인 원소만 저장
  원소의 key가 저장 위치를 결정
```

강사는 이 차이를 extrinsic semantics와 intrinsic semantics로 설명한다. 순차 자료구조에서 위치는 원소 바깥에서 부여한 순서이고, 직접 접근 배열에서 위치는 원소가 가진 key에 연결된다. 배열이라는 메모리 구조가 갑자기 달라진 것이 아니라, 그 칸을 사용하는 의미와 규칙이 달라진 것이다. 같은 배열도 어떤 불변식을 부여하느냐에 따라 다른 자료구조가 된다.

직접 접근의 `O(1)`은 배열 접근이 상수 시간이라는 계산 모델에 따른다. 객체 전체를 인덱스로 쓸 수 있다는 뜻이 아니라, 저장 위치로 사용할 수 있는 정수 key가 있어야 한다. 또한 그 key가 배열 범위 안에 있고, 단일 슬롯으로 관리할 경우 서로 구별된다는 전제가 필요하다. 이 전제들은 뒤의 정렬 알고리즘에서도 계속 중요하다.

### B04. 2:55~5:23 키 공간과 해싱

직접 접근 배열의 문제는 탐색 시간이 아니라 공간이다. 실제 저장할 원소가 `n`개여도 key가 넓은 범위에 퍼져 있으면 배열은 그 전체 범위를 담아야 한다. 강의의 예시는 MIT ID처럼 값의 범위가 원소 수보다 훨씬 클 수 있는 식별자다. 저장할 학생 수는 작아도 가능한 ID의 범위를 전부 배열로 만들면 비어 있는 칸이 매우 많아진다.

이를 해결하기 위해 큰 key 공간을 더 작은 배열 범위로 보내는 해싱을 사용한다. 다만 서로 다른 key가 같은 칸으로 갈 수 있으므로 충돌을 처리해야 한다. 강의에서는 각 칸에 체인을 두는 방식을 복습한다. 충돌한 원소를 찾기 위해 그 체인의 일부 또는 전부를 탐색하므로 체인의 길이가 성능을 결정한다.

고정된 hash function 하나가 모든 입력에 대해 좋은 분포를 보장하는 것은 아니다. 어떤 함수에 대해서는 나쁜 입력을 골라 같은 칸으로 원소를 몰아넣을 수 있다. 그래서 지난 강의에서는 hash family 안에서 함수를 무작위로 고르는 분석을 했다. 여기서 기대값은 입력 자체가 무작위라는 가정만을 뜻하지 않는다. 고정된 입력에 대해서도 알고리즘이 선택하는 hash function의 무작위성에 대해 기대값을 취할 수 있다.

```text
큰 정수 key 공간
      |
      v
무작위로 고른 hash function
      |
      v
작은 배열의 bucket
      |
      v
충돌 원소들의 chain
```

강사는 입력을 정하는 쪽이 알고리즘이 어떤 난수를 고를지 미리 모르는 상황을 강조한다. 적절한 크기의 테이블과 함수군을 쓰면 기대 체인 길이가 상수 규모가 되고, 탐색·삽입·삭제의 기대 시간을 상수로 분석할 수 있다. 무작위 선택의 기대 성능과 모든 선택에서의 최악 성능을 같은 주장으로 읽으면 안 된다.

### B05. 5:23~9:45 최악, 기대, 상각 시간과 질의응답

5:23부터 강사는 set interface를 구현하는 여러 구조를 비교하는 표를 언급한다. 대본에는 판서 표의 모든 행과 열이 들어 있지 않으므로 정확한 표 전체를 복원하지 않는다. 발화에서 확인되는 요점은 sorted array, direct access array, hash table이 같은 find·insert·delete 인터페이스를 다른 비용으로 구현한다는 것이다. 인터페이스가 같다고 실행시간 보장이 같은 것은 아니다.

해시 테이블의 최악 상황은 모든 원소가 같은 bucket에 모이는 경우다. 연결 체인을 단순히 탐색하면 한 번의 조회에 `O(n)` 시간이 들 수 있다. 강사는 이런 최악 상황에서 sorted array의 이진 탐색보다도 나쁠 수 있다고 설명한다. 한 번이라도 선형 시간 조회가 발생하면 안 되는 요구사항이라면 기대 시간만 좋은 구조를 그대로 선택할 수 없다.

체인 자체를 더 효율적인 set 자료구조로 구성할 수 있다는 설명도 나온다. 강사는 Java의 충돌 처리를 예로 들며, 다음 강의에서 이야기할 구조를 체인에 사용할 수 있다고 말한다. 이것은 강의 당시의 설명이며 현재 Java 구현의 모든 조건을 검증한 내용은 아니다. 여기서 받아야 할 개념은 충돌 처리 구조도 설계 선택이며 단순 연결 리스트만이 유일한 선택은 아니라는 점이다.

7:07에는 MIT p set 2가 최악 시간 보장을 요구하므로 해시 테이블을 쓰지 않는 편이 좋겠다는 언급이 있다. 이 말을 성균관대 Min-Max-Median 과제의 별도 금지 조건으로 옮기지는 않는다. 강의 사례와 우리 과제 명세는 구분한다.

7:12 이후 질문은 표의 아래첨자 `e`가 무엇이냐는 것이다. 강사는 `e`가 expected runtime, `a` 또는 `A`가 amortized runtime을 나타낸다고 답한다.

| 분석 종류 | 무엇을 대상으로 하는가 | 해싱 복습에서의 의미 |
| --- | --- | --- |
| Worst-case | 허용된 상황 중 가장 나쁜 경우 | 모든 원소가 한 체인에 있으면 선형 탐색 |
| Expected | 무작위 선택에 대한 평균적 비용 | 좋은 함수군에서 고른 함수의 기대 체인 길이 |

해시 테이블의 적재 정도가 목표에서 크게 벗어나면 더 큰 크기와 새 hash function으로 전체를 다시 만들 수 있다. 한 번의 재구축은 비싸지만 너무 자주 일어나지 않게 설계하면 연산열 전체의 상각 비용으로 설명할 수 있다. 강사는 dynamic array의 크기 확장과 유사한 논리라고 연결한다. Python의 dictionary, set, 객체의 속성 매핑도 해싱의 응용 사례로 언급한다. 이 역시 발화상의 사례이지 Python의 최신 구현 세부를 분석한 것은 아니다.

8:17에는 반대로 key 범위가 충분히 작거나 개발자가 작은 식별자를 직접 부여할 수 있다면 해싱을 굳이 쓸 필요가 없다고 말한다. 작은 직접 접근 배열은 단순하고 조회가 빠르다. C와 C++ 개발 환경의 자료구조 접근성도 짧게 언급하지만, 언어가 직접 접근 배열의 수학적 조건을 바꾸는 것은 아니다.

9:07의 마지막 질문은 build가 왜 expected인지에 관한 것이다. 일반적인 set 삽입은 같은 key가 이미 있는지 체인에서 확인할 수 있으므로 그 탐색 비용이 기대 시간 분석에 들어간다. 모든 key가 서로 다르다는 사실이 입력 조건으로 보장된다면 중복 확인을 생략하고 각 원소를 체인에 추가할 수 있다. 강사는 이 경우 build를 최악 선형 시간으로 할 수 있다고 설명한다. 이 발언을 이후의 모든 hash lookup도 최악 상수라는 뜻으로 확대하면 안 된다. 초기화 크기와 체인 삽입 방식 역시 실제 구현 비용에 포함해야 한다.

### B06. 9:45~15:05 정렬의 결정 트리

9:45부터 주제가 탐색에서 정렬로 바뀐다. insertion sort와 selection sort는 일반적으로 이차 규모의 수행시간을 가졌고, merge sort는 `n log n` 규모였다. 강의의 새 질문은 이보다 더 좋은 정렬 알고리즘이 가능한가이다. 답은 사용하는 연산 모델에 따라 달라진다. 우선 비교만 허용하는 모델에서는 최악 `n log n` 규모보다 일반적으로 더 빨라질 수 없다는 점을 설명한다.

결정 트리에서 내부 노드는 비교이고, 가지는 비교 결과, 잎은 비교를 모두 마친 뒤 정하는 출력이다. 하나의 실행은 루트에서 특정 잎까지 내려가는 경로다. 따라서 그 경로 길이는 실행한 비교 수와 연결된다. 비교당 분기 수가 상수이면 잎의 개수가 커질수록 필요한 높이는 로그 규모로 증가한다.

```text
         비교 1
        /      \
     비교 2    비교 3
     /   \      /   \
   출력  출력  출력  출력

경로 길이 = 해당 입력에서 필요한 비교의 수
가장 긴 경로 = 최악 비교 횟수
```

탐색에서는 가능한 결과가 `n`개 정도였지만 정렬에서는 가능한 순열의 수를 구해야 한다. 서로 다른 원소 `n`개를 정렬한다고 하자. 첫 번째 원소가 차지할 수 있는 위치는 `n`개, 그다음 원소는 남은 `n-1`개, 다음은 `n-2`개다. 이 선택 수를 곱하면 `n!`개의 순열이 나온다.

여기서 같은 숫자 집합을 정렬하면 출력 숫자열은 하나인데 왜 출력이 `n!`개인가라는 혼동이 생길 수 있다. 알고리즘은 원래 입력의 어느 원소가 어느 위치로 가야 하는지를 key의 순서에 따라 구별해야 한다. 원소를 고정된 이름표로 생각하고 가능한 상대적 순서가 달라지는 입력 전체를 고려하면, 그 입력에 필요한 재배열 순열도 `n!`가지가 된다. 이것은 주어진 한 입력에서 정답이 여러 개라는 뜻이 아니다.

14:21~14:59에는 판서 표현을 정정하는 대화가 있다. 강사는 잎 수가 정확히 또는 Theta로 `n!`라고 쓰는 대신 적어도 `n!`, 즉 `Omega(n!)`임을 강조한다. 서로 다른 경로가 같은 출력에 도달할 수도 있어 실제 알고리즘의 결정 트리는 필요한 경우보다 더 많은 잎을 가질 수 있다. 하한 증명에는 잎이 최소한 몇 개 필요한지가 중요하다.

높이 `h`인 이진 트리는 잎을 최대 `2^h`개 가진다. 정렬 알고리즘은 적어도 `n!`개의 가능한 순서를 구별해야 하므로 `2^h >= n!`, 따라서 `h >= log2(n!)`이다. 결과적으로 적어도 한 실행 경로는 이 높이만큼 비교해야 한다. 이는 최악의 경우 하한이며 모든 입력이 꼭 똑같은 수의 비교를 한다는 뜻은 아니다.

### B07. 15:05~17:43 로그 팩토리얼과 비교 정렬 하한

남은 질문은 `log(n!)`가 얼마나 큰가이다. 강사는 Stirling formula를 대입할 수도 있다고 언급하지만, 여기서는 곱의 일부만 사용한 간단한 하한을 보여 준다. 대본의 `Sterling`은 이 공식을 가리키는 전사 표현이며 교안에서는 일반적인 명칭 Stirling으로 표기한다.

```text
n! = 1 * 2 * 3 * ... * n

이 가운데 뒤쪽 약 n/2개의 인수는 각각 n/2 이상

n! >= (n/2)^(n/2)            [짝수 n으로 먼저 생각한 형태]

log2(n!) >= (n/2) * log2(n/2)
          = (n/2) * (log2(n) - 1)
          = Omega(n log n)
```

16:46 이후 학생이 `n/2`를 묻자 강사는 인수가 총 `n`개이고 그중 절반은 `n/2`보다 크거나 같다는 점을 다시 설명한다. 그 절반의 인수를 실제 값보다 작은 `n/2`로 바꾸고 나머지 양의 인수들을 생략해도 원래 곱보다 크지 않은 값을 얻는다. 그 작은 곱에 로그를 취하기 쉬우므로 원하는 하한이 나온다.

홀수 `n`에서는 개수를 floor 또는 ceil로 적어 같은 논리를 적용한다. 예를 들어 뒤쪽 `ceil(n/2)`개 정도의 인수가 모두 `n/2` 이상이며, 이를 통해 얻는 하한도 동일한 점근적 규모다. 특정 짝수 입력에만 성립하는 결론이 아니라 충분히 큰 모든 `n`에 대해 상수배 하한을 잡는 것이 목표다.

강의에서 비교 정렬의 불가능성을 보일 때 필요한 것은 이 하한이다. 문장 `log(n!) = Theta(n log n)`를 완성하려면 상한도 필요하다. 복습용으로 연결하면 각 인수가 `n` 이하이므로 `n! <= n^n`, 따라서 `log(n!) <= n log n`이다. 이 상한 연결은 대본의 하한 설명에 덧붙인 교안 보강이며 강사가 이 구간에서 그대로 읽은 문장으로 취급하지 않는다.

결정 트리 결과와 합치면 비교 정렬의 최악 수행시간은 `Omega(n log n)`이다. merge sort는 같은 규모의 상한을 달성하므로 점근적 의미에서 최적인 비교 정렬이다. 최적이라는 말은 모든 입력 크기에서 가장 빠른 실제 프로그램이거나 상수 계수까지 최소라는 뜻이 아니다. 비교 모델에서의 성장률을 말한다.

마지막으로 이 논증의 전제를 남겨야 한다. 입력 원소들의 순서는 비교 결과로 구분하며, 서로 다른 원소들의 모든 상대적 순서를 일반적으로 처리한다. 정수 key를 메모리 인덱스로 바로 쓰거나 자릿수를 추출하는 것은 이 제한된 모델보다 더 강한 정보를 사용하는 방식이다. 따라서 아래의 선형 정렬은 이 정리를 반박하지 않는다.

### B08. 17:43~23:40 Direct Access Array Sort

17:43에는 지난 탐색에서 쓴 random access 아이디어를 정렬에도 적용할 수 있느냐는 질문이 나온다. 여기서는 key가 서로 다른 정수이고 작은 범위 안에 있다는 전제를 먼저 준다. 학생의 제안은 key를 인덱스로 써서 넣은 뒤 배열을 순서대로 읽자는 것이다. 강사는 이를 임시로 direct access array sort라고 부른다.

```text
입력: key가 서로 다른 n개 원소, 0 <= key < u

1. 길이 u의 비어 있는 직접 접근 배열 D를 만든다.
2. 각 원소 x를 D[x.key]에 저장한다.
3. D[0], D[1], ..., D[u-1]을 순서대로 확인한다.
4. 비어 있지 않은 칸의 원소를 결과에 차례로 넣는다.
```

출력 순서가 정렬되는 이유는 읽는 인덱스가 작은 key부터 큰 key까지 증가하기 때문이다. 비교해서 자리를 찾은 것이 아니라 key가 곧 위치가 되도록 배치했다. key가 없는 칸은 비어 있으므로 건너뛴다. 서로 다른 key라는 조건 덕분에 같은 칸에 두 원소가 들어가 기존 원소를 덮어쓰는 문제가 없다.

| 단계 | 비용 | 이유 |
| --- | --- | --- |
| 배열 생성·빈 칸 초기화 | O(u) | key 공간 전체에 대한 슬롯 준비 |
| n개 원소 저장 | O(n) | 각 원소당 인덱스 접근과 저장이 상수 시간 |
| 배열 순회와 출력 | O(u + n) | 모든 슬롯을 보고 실제 원소를 반환 |
| 총 시간 | O(n + u) | 두 변수의 비용을 모두 남겨야 함 |
| 보조 공간 | O(u), 별도 출력까지 O(n + u) | 배열 길이는 실제 원소 수가 아니라 key 범위 |

key가 서로 다르면 key 공간은 적어도 원소들을 담을 만큼 커야 한다. `u = Theta(n)`이면 `O(n + u) = O(n)`이므로 선형 정렬이 된다. 그러나 `u`가 훨씬 크면 초기화와 순회가 병목이다. 배열 접근 한 번이 상수라고 해서 길이 `u`의 배열 전체를 읽는 것도 상수라는 결론은 나오지 않는다.

22:08부터 key를 입력에 어떻게 붙이느냐는 질문이 나온다. 강사는 set interface에서 원소가 key를 갖는 것은 입력에 부여한 모델이라고 답한다. 원소는 key뿐 아니라 다른 정보를 함께 가진 객체일 수 있다. 정렬 과정에서는 객체 전체를 옮기고 key만 위치 결정에 사용한다. 정수 자체를 정렬한다면 그 정수가 곧 key라고 생각하면 된다.

23:04~23:40에는 이 알고리즘이 작은 범위와 unique key라는 꽤 제한적인 조건에 의존한다는 점을 정리한다. 다음 단계에서는 범위가 더 큰 경우와 key가 중복되는 경우를 각각 해결한다. 이 두 문제는 서로 다르다. 범위 확대는 자릿수 분해로, 동일한 key의 여러 객체는 순서를 보존하는 버킷으로 연결된다.

### B09. 23:40~29:06 큰 정수를 작은 자릿수로 분해

원래 key 범위가 `n^2` 규모라면 그 전체 크기의 직접 접근 배열은 이차 시간과 공간을 요구한다. 앞에서 얻은 선형 정렬의 장점이 사라진다. 학생은 큰 수를 작은 두 수로 나눠 정렬할 수 있지 않느냐고 제안하고, 강사는 이를 base n 표현으로 설명한다.

`0 <= K < n^2`인 정수는 아래처럼 두 자리로 나타낼 수 있다.

```text
a = floor(K / n)
b = K mod n
K = a*n + b

0 <= a < n
0 <= b < n
```

`a`는 더 중요한 상위 자리, `b`는 덜 중요한 하위 자리다. 정수 나눗셈의 몫과 나머지를 이용하면 다시 원래 key를 복구할 수 있다. 숫자를 근사하거나 정보를 버린 것이 아니라 정확한 다른 표현으로 바꾼 것이다. 대본에서 `a`, `b`라는 문자를 썼으며 여기서 `b`는 일반 진법을 가리키는 기호가 아니라 두 번째 자리라는 점에 주의한다.

강의 예제는 `17, 3, 24, 22, 12`이고 원소 수는 `n = 5`다. 따라서 base 5로 표현한다.

| 원래 K | floor(K/5) | K mod 5 | 두 자리 표기 |
| --- | --- | --- | --- |
| 17 | 3 | 2 | (3, 2), 즉 32 |
| 3 | 0 | 3 | (0, 3), 즉 03 |
| 24 | 4 | 4 | (4, 4), 즉 44 |
| 22 | 4 | 2 | (4, 2), 즉 42 |
| 12 | 2 | 2 | (2, 2), 즉 22 |

표의 `32`는 십진수 32가 아니라 base 5의 두 자리를 이어 쓴 것이다. `(3,2)`의 실제 정수 값은 `3*5+2 = 17`이다. 강의에서 표기를 간략하게 하면서 숫자와 자리 표현이 섞이므로 원래 값, 상위 자리, 하위 자리를 분리해서 읽는 것이 안전하다.

이제 각 자릿수는 0~4의 작은 범위에 있다. 전체 정수의 공간을 길이 25의 배열로 다루는 대신, 길이 5짜리 key 공간에 대한 정렬을 몇 번 수행하는 방향을 생각할 수 있다. 다만 원래 정수들이 서로 다르더라도 자릿수는 중복된다. 상위 자리 4와 하위 자리 2가 여러 번 나오므로 앞의 unique-key 전제가 그대로 유지되지는 않는다.

28:27에는 몫·나머지 계산이 컴퓨터에서 상수 시간 연산이라는 설명과 Python `divmod(K,n)`의 언급이 있다. 이것은 word 크기 정수 연산을 기본 연산으로 세는 수업 모델에 따른다. 길이가 제한되지 않은 큰 정수의 나눗셈까지 언제나 상수 시간이라는 주장은 아니다. 교안의 모든 선형 시간 결론도 처리할 key와 자릿수 연산의 모델을 함께 전제한다.

### B10. 29:06~35:02 Tuple Sort와 잘못된 정렬 순서

tuple은 원소의 여러 key를 묶은 표현이다. 강사는 Excel spreadsheet에서 여러 열에 우선순위를 주어 정렬하는 예로 설명한다. 첫 번째 열이 더 중요하고 두 번째 열이 덜 중요하다면, 최종 순서는 먼저 첫 열을 비교하고 같을 때 둘째 열을 비교하는 식이다. 이를 두 자리 정수에 적용하면 상위 자리 `a`가 먼저이고 하위 자리 `b`가 다음이다.

왜 상위 자리가 더 중요한가? 같은 `a` 안에서는 `b`가 값을 구별하지만, `a`가 1 커지면 `b`가 어떤 허용 값이든 원래 수는 더 큰 구간에 속한다. `K = a*n+b`에서 `b`는 `n`보다 작기 때문이다. 따라서 하위 자리만 먼저 또는 마지막으로 우선하는 결과는 원하는 전체 숫자 순서와 다를 수 있다.

강사가 강조하는 것은 어느 자리가 중요한가와 어느 자리부터 정렬하는가를 구분하는 일이다. 가장 중요한 자리부터 전체 배열을 정렬한 뒤 덜 중요한 자리로 전체 배열을 다시 정렬하면, 마지막 정렬이 이전의 그룹 순서를 깨뜨릴 수 있다.

강의 예제를 안정적으로 처리했다고 가정해 중간 배열을 재구성하면 다음과 같다. 대본의 판서 순서를 그대로 복제한 것이 아니라 실패 원인을 확인하기 위한 재구성이다.

```text
입력 (base 5):       32, 03, 44, 42, 22

상위 자리 먼저:      03, 22, 32, 44, 42
하위 자리로 다시:    22, 32, 42, 03, 44

최종 배열은 하위 자리에 의해 크게 그룹화됨.
03이 22, 32, 42보다 뒤에 있으므로 전체 숫자 순서가 아님.
```

이 실패는 불안정 정렬만의 문제가 아니다. 두 단계가 각각 안정적이어도 우선순위의 적용 순서를 잘못 잡으면 최종 결과가 잘못된다. 마지막에 적용한 전체 정렬 기준이 최우선 기준이 되기 때문이다. 그래서 전체 배열을 자리마다 반복 정렬하는 tuple sort에서는 덜 중요한 자리부터 시작하고 가장 중요한 자리를 마지막에 처리한다.

여러 열이 있는 경우도 같은 원리다. 우선순위가 A, B, C 순이라면 이 방식의 실제 정렬 순서는 C, B, A이다. 단 각 단계가 안정적이어야 한다. 상위 key가 같은 원소 사이에서 이전 단계가 만든 하위 key의 순서를 잃지 않아야 하기 때문이다. 다음 구간은 정렬 순서를 바꿨는데도 안정성을 놓치면 왜 실패하는지를 보여 준다.

### B11. 35:02~37:10 안정 정렬이 필요한 이유

하위 자리부터 시작하면 다음 중간 상태를 얻는다.

```text
입력:                32, 03, 44, 42, 22
하위 자리 안정 정렬: 32, 42, 22, 03, 44
```

여기서 상위 자리로 정렬할 때 상위 자리가 4인 두 원소 `42`, `44`가 같은 key다. 이 둘이 입력에 들어온 상대 순서는 `42`가 앞, `44`가 뒤였다. 그런데 상위 자리만 보고 두 원소를 `44`, `42`로 내보내면 이미 맞춰 둔 하위 자리 순서를 깨뜨린다. 강사는 일부러 이런 결과를 써 학생들에게 무엇이 잘못됐는지 묻는다.

stable sorting algorithm은 현재 정렬 기준이 같은 원소들의 입력 상대 순서를 출력에서도 보존한다. 여기서 입력은 최초 배열만이 아니라 현재 정렬 단계에 들어온 배열이다. 첫 패스가 만든 순서가 두 번째 패스의 입력 순서가 되고, 두 번째 패스는 자신의 key가 같은 경우 그 순서를 유지해야 한다.

```text
상위 자리의 key가 같음: 42와 44는 모두 4

안정적이면:            ... 42, 44
불안정할 수 있으면:     ... 44, 42

올바른 두 번째 패스:    03, 22, 32, 42, 44
십진수로 복원:          3, 12, 17, 22, 24
```

이 논리를 짧게 정리하면, 상위 자리가 다른 원소는 두 번째 정렬이 상위 자리 순서를 결정하고, 상위 자리가 같은 원소는 안정성 덕분에 이미 정렬된 하위 자리 순서를 유지한다. 두 경우를 합하면 상위 자리와 하위 자리 전체의 사전식 순서가 된다. 반복 정렬의 correctness는 바로 이 연결에 의존한다.

안정성은 같은 숫자 두 개가 눈으로 똑같다는 문제만이 아니다. 객체에는 다른 자리나 부가 정보가 함께 있을 수 있다. 현재 key가 같더라도 다른 정보의 순서를 보존해야 다음 계산에 쓸 수 있다. 따라서 원래 정수 key가 unique라는 사실만으로 각 자리 정렬의 안정성을 생략할 수 없다.

### B12. 37:10~39:29 상위 자리부터 그룹화하는 대안에 대한 질문

학생은 먼저 상위 자리로 정렬한 뒤 같은 상위 자리를 가진 그룹 안에서 하위 자리를 정렬하면 되지 않느냐고 묻는다. 강사는 그런 접근도 가능하다고 인정한다. 하지만 그룹마다 어떤 정렬 알고리즘을 쓰며 비용을 얼마나 지불하는지 분석해야 한다고 말한다. 한 그룹에 많은 충돌 원소가 몰릴 수도 있으므로 그룹 내부를 아무 방식으로 정렬해도 자동으로 선형이 되는 것은 아니다.

이 발언을 모든 상위 자리 우선 정렬이 잘못되거나 항상 이차 시간이라는 일반 정리로 읽으면 안 된다. 이 강의는 더 단순하게 작은 자리부터 전체 배열을 안정 정렬하는 방법을 선택한다. 이미 논의한 작은 key 공간에 대한 정렬을 상수 번 조합해 비용을 설명하기 쉽기 때문이다. 세부적인 다른 알고리즘은 이 대본의 범위를 넘으므로 새 단원으로 추가하지 않는다.

38:34에는 현재 tuple이 두 자리뿐이므로 정렬을 두 번 하면 된다는 점을 강조한다. 상수 개의 패스가 각각 선형 시간이라면 전체도 선형 시간이다. 그러나 아직 각 패스의 실제 정렬 도구를 정하지 않았다. direct access array sort를 그대로 쓸 수 있느냐는 질문에서 다음 문제가 드러난다.

앞의 direct access array sort는 같은 key가 없다고 가정했다. 자릿수로 나누고 나니 상위 4, 하위 2처럼 같은 key가 나온다. 한 칸에 원소 하나만 넣으면 다른 원소를 덮어쓴다. 원소가 사라지는 것은 정렬 순서 이전에 출력이 원래 입력의 순열이어야 한다는 조건을 위반한다. 따라서 중복 key를 저장하면서 상대 순서도 유지하는 장치가 필요하다.

39:16 이후 학생이 한 key에 여러 원소를 넣거나 list를 두면 되지 않느냐고 제안한다. 강사는 이것이 원하는 방향이라고 답하고 counting sort라는 이름으로 연결한다. 이 구간의 역할은 안정성이 왜 필요한지에서 안정성을 실제로 구현할 자료구조로 넘어가는 것이다.

### B13. 39:29~42:44 버킷과 체인으로 설명하는 Counting Sort

이 영상의 Counting Sort 설명은 key별 버킷에 순서 보존 체인을 두는 방식이다. 교재에서 자주 보는 개수 배열·누적합·출력 위치 계산 방식과 같은 문제를 해결하지만, 강사가 이 대본에서 전개한 구현 설명을 임의로 누적합 설명으로 바꾸지 않는다.

`0 <= key < u`의 직접 접근 배열을 만들되, 각 칸에 원소 하나 대신 sequence를 둔다. sequence는 원소가 들어온 순서를 보존하는 구조다. 동적 배열이나 꼬리 포인터가 있는 연결 리스트처럼 뒤에 추가하고 앞부터 순서대로 읽을 수 있으면 된다. 입력을 왼쪽부터 읽으며 현재 key의 버킷 끝에 원소를 추가하고, 마지막에 key가 작은 버킷부터 읽는다.

```text
stable_bucket_sort(A, key_range):
    buckets = key_range개의 빈 sequence
    for x in A, 입력 순서대로:
        buckets[x.key]의 끝에 x를 추가
    result = 빈 sequence
    for k = 0 ... key_range-1:
        buckets[k]를 저장된 순서대로 읽어 result에 추가
    return result
```

이 의사코드는 대본의 동작을 정리한 것이며 제출용 코드가 아니다. 실제 구현에서는 동적 배열 확장의 상각 비용이나 연결 리스트의 꼬리 추가 비용 등을 분석해야 한다. 매번 끝을 찾으려고 체인 전체를 다시 읽는 구현은 강의가 전제한 상수 시간 추가를 충족하지 않는다.

앞의 하위 자리 정렬 결과를 상위 자리로 정렬하면 다음처럼 저장된다.

```text
두 번째 패스 입력: 32, 42, 22, 03, 44
정렬 key: 상위 자리

bucket 0: 03
bucket 1: (empty)
bucket 2: 22
bucket 3: 32
bucket 4: 42 -> 44

key 오름차순으로 버킷 순회:
03, 22, 32, 42, 44
```

`bucket 4`에서 `42` 뒤에 `44`를 추가했으므로 두 원소의 상대 순서가 유지된다. 새 원소를 무조건 리스트 앞에 넣으면 같은 bucket의 원소 순서가 뒤집힐 수 있다. key가 같을 때 아무 순서로 출력하면 단일 자리 기준으로는 정렬된 것처럼 보여도 tuple sort의 이전 작업을 지킬 수 없다.

버킷마다 저장된 원소들이 정확히 입력 순서대로 나가므로 안정성이 성립한다. 버킷을 작은 key부터 순회하므로 현재 key에 대한 정렬도 성립한다. 각 원소가 자기 버킷에 정확히 한 번 저장되고 한 번 출력되므로 입력 원소의 보존도 성립한다. 이 세 가지가 이 구조의 correctness를 구성한다.

### B14. 42:44~45:15 Counting Sort의 비용과 질의응답

버킷이 `u`개라고 해서 버킷마다 `n`개를 다시 정렬하는 것은 아니다. 실제로 저장되는 원소 수의 합은 정확히 `n`이다. 어떤 버킷이 길면 다른 버킷은 그만큼 적은 원소를 갖는다. 따라서 버킷을 모두 읽는 비용은 key 슬롯을 확인하는 `u`와 실제 원소들을 방문하는 `n`을 합쳐 계산한다.

```text
버킷별 길이: l0, l1, ..., l(u-1)

l0 + l1 + ... + l(u-1) = n

초기화:       O(u)
모든 삽입:    O(n), 상수 시간 꼬리 추가를 가정
모든 출력:    O(u + sum(lk)) = O(u + n)
총 시간:      O(n + u)
총 보조 공간: O(n + u)
```

강사는 버킷당 상수 정도의 관리 정보가 필요하므로 `u`의 overhead가 생기고, 각 실제 원소는 한 번 저장되므로 `n`의 공간이 더해진다고 설명한다. 동적 배열을 버킷으로 쓴 경우 개별 append가 늘 최악 상수는 아닐 수 있으나 일반적인 확장 방식에서는 전체 append 비용을 상각 분석할 수 있다. 최악 선형 build를 주장할 때는 그러한 비용의 근거 또는 실제 상수 시간 연결 추가 구조를 명시해야 한다.

43:44의 질문은 같은 key의 원소들이 들어 있는 리스트 내부가 어떻게 정렬되는가이다. 강사의 답은 버킷 안에서 새로 정렬하지 않는다는 것이다. 입력에 들어온 순서만 보존한다. 앞선 하위 자리 정렬이 이미 그 원소들을 올바른 순서로 만들었으므로, 같은 상위 자리에서 충돌하면 기존 순서가 바로 원하는 하위 자리 순서다.

이는 첫 번째 패스에서 모든 부가 정보가 정렬돼 있어야 한다는 뜻은 아니다. 처음에는 가장 낮은 자리만 정렬하고, 다음에는 이미 처리한 낮은 자리들의 순서를 보존한다. 처리한 자리의 수가 늘수록 불변식이 넓어지는 구조다.

44:39의 질문은 배열 크기가 `u`가 아니라 `n` 아니냐는 것이다. 강사는 일반적인 Counting Sort의 key 공간은 `u`이며, 이 예제에서는 base n의 한 자리를 정렬하므로 우연히 `u=n`으로 선택했다고 설명한다. Counting Sort 자체가 모든 입력에서 항상 길이 `n` 배열만 쓰는 알고리즘은 아니다. 일반 비용 `O(n+u)`와 이 예제의 대입 `u=n`을 구분해야 한다.

### B15. 45:15~47:39 두 자리에서 여러 자리로 확장

이제 tuple sort의 각 패스에 stable Counting Sort를 사용할 수 있다. `0 <= K < n^2`이면 base n에서 두 자리로 표현되므로 두 패스가 필요하다. 한 자릿수의 key 공간은 `n`이고 정렬할 객체도 `n`개이므로 각 패스는 `O(n+n)=O(n)`이다. 두 번을 합쳐도 `O(n)`이다.

원래 숫자가 `n^3` 미만이면 base n에서 세 자리다. 강사는 `n`으로 나누면 남는 몫이 `n^2` 규모이고 그 몫을 다시 두 자리로 나누면 된다고 설명한다. 세 자리도 상수 개이므로 낮은 자리부터 세 번의 stable sort로 처리할 수 있다. 각 단계의 비용이 선형이고 단계 수가 3이면 전체 선형이라는 분석은 두 자리와 같다.

```text
K < n^2 -> base n의 두 자리 -> Counting Sort 2번 -> O(n)
K < n^3 -> base n의 세 자리 -> Counting Sort 3번 -> O(n)
K < n^c -> base n의 c자리 이내 -> O(c*n)
```

여기서 `c`는 입력 크기에 따라 계속 커지는 변수가 아니라 고정된 상수일 때 선형 결론을 준다. 자릿수가 늘어난다는 사실을 무시하고 반복 횟수를 언제나 상수라고 쓸 수는 없다. 범위를 일반화할 때는 자릿수를 별도의 변수로 둬야 한다.

47:12 질문은 각 정렬의 비용이 여전히 `O(n+u)`인지에 관한 것이다. 강사는 그렇다고 답하면서 지금은 자릿수의 범위를 `n`으로 제한했기 때문에 그 식의 `u`에 `n`을 넣는 것이라고 설명한다. 원래 숫자의 범위 `n^2`나 `n^3`를 한 자리 Counting Sort의 버킷 수로 넣는 것이 아니다. 큰 공간을 작은 공간의 여러 패스로 분해했기 때문에 이득을 얻는다.

### B16. 47:39~51:47 Radix Sort의 알고리즘과 분석

강사는 지금까지 조합한 아이디어를 Radix Sort라고 부른다. 정수 key를 base n의 tuple로 분해하고, 가장 덜 중요한 자리부터 가장 중요한 자리까지 Counting Sort로 안정 정렬한다. 각 자리의 범위를 작게 유지하는 것과 기존 하위 자리 순서를 보존하는 것이 함께 필요하다.

```text
입력: n개의 정수 key, 0 <= key < U
전제: n >= 2, key와 자릿수 계산이 수업의 word 연산 모델에 맞음

1. 각 정수를 base n의 d자리로 나타낸다.
2. 부족한 높은 자리는 0으로 채워 같은 자리 위치를 사용한다.
3. position = 0부터 d-1까지:
       해당 자리를 key로 하는 stable Counting Sort를 수행한다.
4. 정렬된 원소들을 반환한다.
```

이 의사코드의 자리 0은 일의 자리, 가장 낮은 자리다. 원소에서 한 자리만 떼어 따로 정렬한 뒤 다른 정보와의 연결을 잃으면 안 된다. 정렬 중 옮기는 대상은 전체 원소이고, 현재 패스의 key만 그 자리 값이다.

교안의 불변식으로 정리하면, 낮은 자리부터 `t`개를 처리한 뒤 배열은 그 `t`개 자리가 나타내는 값에 대해 정렬돼 있다. 다음 자리 stable sort는 그 자리 값이 다른 경우 새 순서를 만들고, 같은 경우 기존의 낮은 `t`자리 순서를 보존한다. 따라서 다음 단계에서는 낮은 `t+1`자리가 정렬된다. 모든 자리를 처리하면 전체 key가 정렬된다. 이 설명은 강의의 안정성 논리를 반복 패스 전체로 재구성한 것이다.

base n에서 `0 <= K < U`인 key를 표현하는 데 필요한 자리 수는 대략 `log_n U`다. 정수 자리 수로는 적어도 한 자리를 사용하는 `d = max(1, ceil(log_n U))`로 생각할 수 있다. `U=1`처럼 모든 값이 0인 경계와 입력 하나인 경우는 별도 단순 처리할 수 있다. 강의의 핵심은 충분히 큰 `n`에서 key 범위와 자리 수의 관계다.

| 작업 | 시간 |
| --- | --- |
| n개 원소를 읽고 관리 | O(n) |
| 각 key의 d자리 표현 생성 | O(n*d) |
| 한 자리에 대한 stable Counting Sort | O(n+n) = O(n) |
| d개 자리에 대한 반복 | O(n*d) |
| 총 시간 | O(n + n*d), 강의 표기 O(n + n log_n U) |

대본에서는 자리 표현을 tuple로 만드는 비용을 따로 센다. 각 원소에 `d`개 자리를 저장하면 그 표현 자체의 공간은 `O(n*d)`다. Counting Sort의 버킷과 결과 관리에는 `O(n)` 규모가 더 필요하다. 따라서 이 대본의 명시적 tuple 생성 방식에 대응하는 공간은 `O(n*d+n)`로 볼 수 있다. 공간 분석은 대본의 저장 방식에서 계산한 교안 보강이다. 일반적인 모든 Radix Sort 구현의 공간이 반드시 이와 같다는 뜻은 아니다.

일반 진법 `b`를 사용해 분석할 때는 각 자리의 범위가 `b`, 자리 수가 `d`이므로 stable Counting Sort를 반복하는 비용이 `O(d*(n+b))`다. 이는 강의의 base n 선택을 비교하기 위한 같은 비용식의 일반 표기다. 이번 영상은 `b=n`으로 선택해 `O(n*d)`를 얻는다. 십진수 자리로 쪼갠다고 무조건 강의와 같은 자리 수가 되는 것은 아니다.

50:23부터 선형 시간이 되는 범위를 묻는다. `U <= n^c`인 고정 상수 `c`가 있으면 `log_n U <= c`이고 자리 수가 상수로 제한된다. 그러면 총 시간은 `O(n)`이다. Counting Sort는 전체 key 공간이 `O(n)`일 때 선형이고, Radix Sort는 전체 key 공간이 `n`의 고정 차수 다항식이어도 선형이 될 수 있다는 차이가 있다.

51:20에는 Counting Sort의 조건 표기에 오타가 있다는 정정이 나온다. 강사는 Counting Sort가 선형인 조건은 `u`가 order n일 때라고 바로잡는다. 이 교안은 정정 후 의미인 `u=O(n)`을 사용한다. 대본의 `counting short`, `rating sort`처럼 문맥상 정렬 이름을 잘못 전사한 부분도 각각 Counting Sort, Radix Sort로 표기한다.

51:41~51:47의 결론은 숫자가 너무 크지 않다는 조건 아래 정수를 선형 시간에 정렬할 수 있다는 것이다. 정수라는 이유만으로 key 크기·자리 수·계산 비용을 모두 무시할 수는 없다. 비교 정렬 하한, key 범위, 안정성, 자리 수를 함께 설명해야 이 강의 전체의 결론이 정확해진다.

### B17. 비교표와 복습 질문

| 방법 | 활용하는 정보 | 중복 key | 비용 | 선형 시간 조건 |
| --- | --- | --- | --- | --- |
| 일반 비교 정렬 | 두 원소의 비교 결과 | 알고리즘에 따라 처리 | 최악 하한 Omega(n log n) | 일반 입력에 대해 이 하한을 넘을 수 없음 |

6. 원래 정수들이 서로 달라도 자릿수 key는 왜 중복될 수 있는가?
7. 높은 자리부터 전체 배열을 반복 정렬하면 이전 작업이 어떻게 깨지는가?

14. unique key를 이용한 build 최적화가 일반 lookup의 최악 상수 보장과 다른 이유는 무엇인가?

핵심 연결을 한 문장으로 적으면 다음과 같다. **비교만으로 모든 순열을 구별하면 로그 팩토리얼만큼의 비교가 필요하지만, 작은 범위의 정수 key를 인덱스로 이용하고 안정 정렬로 자리 정보를 누적하면 그 비교 모델 밖에서 선형 정렬을 만들 수 있다.**

앞부분은 특정 정렬 알고리즘의 실행 시간을 계산하는 수업이 아니다. 비교만 사용하는 모든 올바른 알고리즘이 피할 수 없는 비용을 구한다. 뒷부분은 그 비교 모델을 벗어나 정수 key를 배열 인덱스로 사용한다. 따라서 강의 제목의 세 요소는 따로 떨어진 단원이 아니라 하한을 증명하고, 그 하한의 적용 조건을 확인하고, 조건 밖의 알고리즘을 설계하는 하나의 흐름이다.

### C02. 전체 구조도

```text
질문: 정렬은 반드시 n log n 시간이 필요한가?
  |

  |     |

  |           |
  |           +-- 탐색: L >= n -> Omega(log n)
  |           +-- 정렬: L >= n! -> Omega(n log n)
  |
  +-- Word-RAM: 정수 구조와 상수 시간 random access 허용
        |

        |     key별 리스트에 item 저장 -> 순서대로 연결
```

### C03. 1:49~4:38 Comparison Model

비교 모델에서는 입력 item을 black box로 취급한다. item의 bit나 숫자 자릿수를 뜯어보지 않고, 두 item을 비교하는 연산으로만 순서 정보를 얻는다. Abstract Data Type이 정해진 연산만 외부에 제공하는 것처럼 생각하면 된다. 강사는 `<`, `<=`, `>`, `>=`, `==` 등의 비교를 허용하며, 각 연산의 결과는 yes 또는 no의 이진 답이다.

이것이 item 이동 자체를 금지한다는 뜻은 아니다. Merge Sort는 원소를 옮기고 포인터도 바꾸지만, 어떤 원소가 먼저 와야 하는지 알아내는 방식은 두 key의 비교다. Heap과 Heap Sort, Binary Search Tree도 같은 의미에서 비교 기반이다. 내부 표현을 이용해 key값 위치의 메모리를 곧바로 읽는 것은 이 모델의 순서 정보 획득 방법이 아니다.

시간 비용은 여기서 **비교 횟수만** 센다. 다른 연산을 무료로 취급하는 것은 실제 프로그램에서 복사나 포인터 변경이 무료라는 주장이 아니라, 하한을 더 강하게 보이기 위한 분석 방식이다. 다른 작업을 전부 공짜로 허용해도 비교를 적어도 일정 횟수 해야 한다면, 비교에 상수 비용이 드는 실제 실행에서도 그 비용 아래로 내려갈 수 없다.

따라서 다음 둘은 구분한다.

| 표현 | 의미 |
| --- | --- |
| 특정 알고리즘이 O(n log n)에 동작 | 그 알고리즘에 대한 상한 분석 |
| 모든 비교 정렬이 최악 Omega(n log n) 비교를 필요로 함 | 같은 모델의 모든 올바른 알고리즘에 대한 하한 |
| Merge Sort가 이 모델에서 최적 | 상한과 하한의 점근적 차수가 일치 |
| 모든 정렬이 모델과 관계없이 n log n 필요 | 이 강의가 증명하지 않는 잘못된 일반화 |

강사가 이전 BST·AVL 수업을 언급하는 것은 MIT 강의 내부의 진행 순서다. 모든 Binary Search Tree가 자동으로 로그 높이라는 뜻은 아니다. 정렬된 배열의 Binary Search나 균형 잡힌 트리는 로그 상한을 달성하지만, 한쪽으로 기울어진 일반 BST는 선형 높이를 가질 수 있다.

### C04. 4:49~10:26 Decision Tree와 세 원소 탐색 예제

Decision Tree는 입력 크기를 고정하고 알고리즘의 가능한 비교 결과를 전부 펼친 분석 도구다. 내부 노드에 비교를 적고, yes/no의 두 가지 결과에 따라 자식으로 간다. 답을 결정한 곳은 leaf다. 특정 입력으로 실행하면 전체 트리를 모두 방문하는 것이 아니라 한 경로만 따라간다.

강의 예제는 정렬된 배열 `A[0], A[1], A[2]`에 대해 새 값 `x`의 위치를 구분한다. 처음 질문은 `A[1] < x?`다. 대본 설명을 트리로 옮기면 다음과 같다.

```text
                         A[1] < x ?
                       /             \
                    NO                 YES
              A[0] < x ?          A[2] < x ?
               /      \             /      \
             NO       YES          NO       YES
          x <= A[0]  A[0]<x<=A[1] A[1]<x<=A[2] x>A[2]
```

왼쪽으로 갔다는 것은 `x <= A[1]`이라는 정보가 이미 있다는 뜻이다. 그 상태에서 `A[0] < x`가 참이면 두 결과를 결합하여 `A[0] < x <= A[1]`을 얻는다. 오른쪽에서도 같은 방식으로 `A[1] < x <= A[2]` 또는 `x > A[2]`를 얻는다. 매 단계의 답은 그 비교 하나뿐 아니라 **앞에서 얻은 정보와 함께** 해석해야 한다.

강사는 정확히 같은 값인지까지 구별하려면 추가 비교가 필요하다고 두 번 언급한다. 이 그림은 `x`가 어느 구간에 있는지를 찾는 축약 예제이지, 네 개 leaf만으로 모든 equality 판정을 끝낸 완전한 membership 검색 코드가 아니다. 예를 들어 `x <= A[0]` leaf에서는 `x < A[0]`인지 `x == A[0]`인지 아직 나누지 않았다.

모든 실행을 그림으로 펼치면 트리가 매우 커질 수 있다. 정렬 알고리즘의 전체 결정 트리는 특히 거대하다. 이 트리를 실제로 메모리에 만들어 실행하라는 것이 아니라, 경로와 답의 개수를 세어 하한을 분석하라는 것이다. 같은 알고리즘의 짧은 반복문·재귀 코드와 아주 큰 결정 트리는 서로 다른 표현이다.

### C05. 10:32~15:00 실행 경로와 트리 높이

강의의 질문과 답을 정리하면 다음과 같다.

| 알고리즘에서의 대상 | Decision Tree의 대응 |
| --- | --- |
| 이진 결과를 얻는 비교 | internal node |
| 계산을 마치고 답을 반환 | leaf |
| 한 입력에 대한 한 번의 실행 | root-to-leaf path |
| 그 실행의 비교 횟수 | 해당 경로의 길이 |
| 알고리즘의 최악 비교 횟수 | 가장 긴 경로의 길이, 즉 height |

예제에서 `A[0] < x <= A[1]`을 얻는 실행은 root에서 한 번, 왼쪽 자식에서 한 번 비교하므로 비용이 2다. 경로의 edge 수도 2다. 레벨을 root부터 1, 2, 3으로 세면 높이는 레벨 수보다 하나 작다는 점을 강사가 확인한다. 여기서는 root의 depth를 0으로 놓고 edge 수로 높이를 센다.

높이 `h`인 이진 트리가 가질 수 있는 leaf는 최대 `2^h`개다. 따라서 반드시 구별해야 할 답이 `L`개라면 다음 관계가 필요하다.

```text
leaf 수 >= L
leaf 수 <= 2^h
따라서 2^h >= L
따라서 h >= ceil(log2 L)
```

이것이 강의 전반부의 핵심 도구다. 알고리즘을 일일이 나열해서 빠르거나 느린지 확인하는 대신, 문제의 답을 구별하려면 트리가 얼마나 높아야 하는지를 묻는다. 다만 **이진 트리이므로 무조건 높이가 log n이다**라고 쓰면 논리가 빠진다. 답의 수로부터 leaf 수의 하한을 먼저 얻어야 한다. 이진 트리도 한쪽으로 길게 늘어지면 훨씬 큰 높이를 가질 수 있다.

Decision Tree 자체는 꼭 수치 비교에만 쓸 수 있는 개념은 아니다. 강사는 다른 이진 결정도 노드에 넣을 수 있다고 설명한다. 그러나 여기서 얻는 탐색·정렬 정리는 item의 순서를 비교만으로 알아내는 모델에 적용한다. 뒤의 RAM 연산을 아무 근거 없이 같은 이진 비교 하나로 바꿔 세지 않는다.

### C06. 15:25~21:22 전처리된 탐색의 하한

탐색 정리는 **미리 전처리한 n개의 item** 가운데 새로운 질의 item을 찾더라도 비교 모델에서는 최악 `Omega(log n)` 비교가 필요하다는 것이다. 전처리 시간은 무료로 준다. 미리 정렬해 두거나 AVL Tree를 만들어 두거나 다른 구조를 설계해도, 아직 주어지지 않았던 `x`를 받은 뒤 어떤 답인지 판정하는 비용은 남는다.

정확히 어떤 탐색 결과를 반환하는가에 따라 가능한 답의 수는 달라진다.

- `x`가 기존의 서로 다른 item 중 하나와 일치하는 경우만 보아도 일치 위치는 n개다.
- `x`가 어느 사이 구간에 들어가는지만 구별하면 양 끝을 포함해 n+1개 구간이 있다.
- 일치와 엄격한 사이 구간을 각각 나누면 2n+1개의 결과를 생각할 수 있다.

이 차이 때문에 로그의 내부가 달라지더라도 점근적으로는 모두 같은 `Omega(log n)`이다. 정리는 최악 입력을 다루므로 서로 다른 key를 가진 경우를 고려할 수 있다. 모든 item이 같은 값인 특수 입력까지 n개의 서로 다른 답을 갖는다고 주장할 필요는 없다.

증명은 다음 세 줄로 연결된다.

```text
가능한 답을 구별하는 leaf가 적어도 n개 필요하다.
비교는 YES/NO이므로 결정 트리는 이진 트리다.
높이 h >= log2 n이므로 최악 비교 횟수는 Omega(log n)이다.
```

하나의 답으로 끝나는 leaf가 여러 개 있어도 괜찮다. leaf가 정확히 n개라고 할 필요가 없다. leaf가 더 많으면 트리 높이에 대한 하한이 약해지는 것이 아니라 유지되거나 더 커진다. 강사의 질문에서 처음 학생 답은 이진 분기만 지적했고, 추가 질문을 통해 **모든 가능한 답을 담을 만큼 leaf가 있어야 한다**는 두 번째 조건이 나온다.

이 결과는 Binary Search의 `O(log n)` 상한과 맞으므로 비교 탐색이 점근적으로 최적이라는 근거다. predecessor, successor처럼 순서상 위치를 묻는 탐색도 같은 관점으로 연결된다. 이것은 비교 모델에서 개선을 멈출 수 있는 기준이며, 정수 인덱싱 같은 다른 모델까지 더 빠른 방법이 없다는 말은 아니다. 18:02~18:20의 학생에게 베개를 건네는 장면과 농담은 원문에 보관하고, 증명 단계로 추가하지 않는다.

### C07. 21:22~25:23 정렬에는 왜 n factorial개의 잎이 필요한가

정렬에서도 internal node는 `A[i] < A[j]?` 같은 비교다. swap은 item을 이동시키는 연산이라 결정 노드로 그리지 않는다. 마지막 leaf에서는 원래 입력의 어느 item을 먼저 놓고 어느 item을 다음에 놓아야 하는지, 즉 정렬된 순열을 결정해야 한다.

강사는 `A[5], A[7], A[1], A[0], ...` 같은 원래 위치의 나열로 leaf의 답을 설명한다. 이것은 특정 네 원소 배열의 실제 정렬 실험이 아니라 **원래 입력의 인덱스로 출력 순서를 표현할 수 있다**는 예시다. key가 모두 다르면 각 위치의 상대적 크기 순서는 n!가지 가능하다.

고정된 leaf는 이미 정해진 비교 결과를 따라 도달한 곳이다. 비교 모델에서는 그 leaf에서 아무 추가 정보 없이 모든 가능한 상대 순서를 동시에 맞힐 수 없다. 서로 다른 정렬 순서를 요구하는 입력들은 적절히 다른 leaf로 구별되어야 한다. 따라서 필요한 leaf 수는 적어도 n!이다. 같은 출력 순서에 여러 경로가 도달해 leaf가 더 많아지는 것은 허용된다.

```text
서로 다른 key n개
  -> 상대 순서 n!가지
  -> 올바른 비교 정렬은 적어도 n!개의 경우를 구별
  -> 결정 트리 leaf >= n!
  -> 2^h >= n!
  -> h >= log2(n!)
```

여기까지는 트리의 논리이고, 다음은 `log2(n!)`이 얼마나 빨리 커지는지 계산하는 수학 단계다. 이 두 단계를 분리하면 증명이 깔끔하다. 정렬 하한을 쓰면서 처음부터 `n log n`이 필요하다고 가정하지 말고, 가능한 답의 수에서 `log(n!)`을 얻은 다음 함수의 성장률을 계산한다.

중복 key가 있는 일부 입력은 가능한 서로 다른 순서가 줄어들 수 있지만 일반 정렬의 최악 하한은 사라지지 않는다. 알고리즘이 처리해야 하는 입력 집합에 서로 다른 key n개의 경우가 포함되기 때문이다. 이 하한은 이 강의의 이진 비교 결정 트리 관점에서의 최악 비교 수를 다룬다. 모든 개별 입력에서 정확히 같은 비교 수를 수행한다는 뜻은 아니다.

### C08. 25:23~28:42 로그 팩토리얼의 합과 절반 하한

학생은 Stirling 근사 또는 로그의 합으로 계산하자고 제안한다. 강사는 먼저 합을 선택한다. 팩토리얼은 곱이고 곱의 로그는 로그의 합이므로 다음과 같다. 아래 `log`는 밑 2다.

```text
log(n!) = log(1*2*...*n)
        = sum(i=1..n) log i
```

상한은 각 항이 `log n` 이하라는 사실만 쓰면 된다.

```text
sum(i=1..n) log i <= n log n
따라서 log(n!) = O(n log n)
```

하한은 모든 항을 똑같이 크게 잡을 수 없으므로, 작은 앞쪽 항을 버리고 **뒤쪽 절반만** 남긴다. 강사는 로그 그래프와 면적을 언급하며 적분을 떠올리지만, 실제 선택한 증명은 적분 없이 절반의 항을 남기는 방식이다. 모든 항이 비음수이므로 앞부분을 버린 합은 원래 합보다 작거나 같다.

짝수 n에서 뒤 절반 `i=n/2+1, ..., n`을 취하면 정확히 n/2개의 항이다. 각 i가 n/2 이상이므로 각 로그는 적어도 `log(n/2)=log n-1`이다.

```text
log(n!) >= sum(i=n/2+1..n) log i
        >= (n/2) log(n/2)
         = (n/2)(log n - 1)
         = (n log n)/2 - n/2
```

이를 명확한 Omega 상수로 쓰고 싶다면 n>=4에서 `log n>=2`이므로 `log n-1 >= (log n)/2`를 이용한다.

```text
log(n!) >= (n log n)/4  (n>=4, 짝수 n)
```

홀수까지 포함하는 설명도 같은 원리다. `i=ceil(n/2), ..., n`의 항을 남기면 적어도 n/2개의 항이 각각 `log(n/2)` 이상이다. 그러므로 같은 하한을 모든 정수 n>=4에 사용할 수 있다. 끝점·floor·ceiling 때문에 정확한 항 수가 한 개 달라지는 것은 상수 차수의 증명을 바꾸지 않지만, 식을 제출할 때는 남기는 범위를 명시하면 좋다.

대본에서 강사는 27:48 부근에 합을 계산하다가 항 수를 n개로 계산하고, 27:58~28:18에 n/2개라고 정정한다. 교안은 정정 후 식을 사용한다. 결과는 `Omega(n log n)`이고, 앞에서 얻은 상한과 합치면 `log(n!)=Theta(n log n)`이다. 정렬 결정 트리에 필요한 것은 그중 하한 방향이다. 즉 `h>=log(n!)`에 대입하여 비교 정렬의 최악 비용을 `Omega(n log n)`으로 결론낸다.

### C09. 28:42~30:16 Stirling 공식과 하한 증명 요약

강사는 두 번째 방법으로 Stirling 공식을 간단히 소개한다.

```text
n! ~ sqrt(2*pi*n) * (n/e)^n
```

여기에 밑 2의 로그를 취하면, 식을 정리했을 때 주요 항은 다음과 같다.

```text
log2(n!) = n log2 n - n log2 e + O(log n)
```

따라서 성장률은 역시 `Theta(n log n)`이다. 강의에서는 `n log n`에서 선형 크기의 항이 빠진다는 수준으로 설명한다. 절반만 남기는 증명은 느슨한 상수를 주지만 차수를 증명하기에는 충분하고, Stirling은 주요 항의 더 정확한 계수까지 보여 준다. 상수를 정밀하게 구하는 것과 점근적 차수만 구하는 것은 다른 목표다.

이 공식 자체를 유도하는 수업은 아니다. 대본에서 근사나 Taylor series를 언급해도, 그것을 근거로 팩토리얼의 Taylor 전개를 새로 만들어 증명에 넣지는 않는다. 복습의 주된 방법은 앞 절의 단순한 합 증명이고, Stirling은 강사가 실제 소개한 대안으로 구분해서 남긴다.

전체 하한 증명 틀은 **이진 결정 -> 필요한 답의 수 -> leaf 하한 -> 높이 하한**이다. 탐색에서는 답이 적어도 n개라 `log n`, 정렬에서는 n!개라 `log(n!)`이 나온다. 정렬 함수의 상한을 알고 있다는 이유만으로 모든 알고리즘의 하한까지 자동으로 성립하는 것이 아니다. 모델과 답의 수를 명시한 뒤 이 연결을 써야 한다.

### C10. 30:16~31:55 전처리와 타이트하지 않은 하한에 대한 질문

학생은 `preprocessed items`가 무슨 뜻인지 묻는다. 강사는 기존 n개 item 사이의 비교를 미리 전부 무료로 수행해도 좋다고 설명한다. 그 뒤 새로운 x를 주며, 그때부터 x와 기존 item의 비교에 비용을 부과한다. 검색 전에 기존 item의 구조를 아무리 잘 알아도 새 질의가 어디에 들어가는지는 구별해야 한다.

정렬 문제에는 이 전처리를 똑같이 적용하지 않는다. **현재 정렬해야 할 입력을 이미 공짜로 정렬해 두었다면** 이후에는 0번의 비교로 끝낼 수 있기 때문이다. 정렬 하한은 아직 순서를 알아내지 않은 입력을 받아 정렬하는 비용을 다룬다. 탐색에서 고정 데이터의 전처리를 허용하는 것과 정렬할 데이터를 이미 처리해 놓는 것은 조건이 다르다.

강사는 전처리하지 않은 탐색에는 일반적으로 선형 비용이 필요하지만, 방금의 leaf-count 방법만으로는 로그 하한밖에 얻지 못한다고 덧붙인다. `Omega(log n)`이라는 명제가 참이어도 실제 필요한 비용이 `Theta(n)`이면 그것은 타이트한 하한이 아니다. 이 증명 도구가 항상 가장 강한 하한을 자동으로 준다는 뜻은 아니다.

```text
하한을 하나 증명했다
  != 그 하한이 가장 정확한 차수다

하한 Omega(log n) + 실제 알고리즘 O(log n)
  -> 로그 차수에서 최적임을 확인

하한 Omega(log n) + 실제 비용 Theta(n)
  -> 하한은 참이지만 더 강한 하한이 필요할 수 있음
```

이 질의응답은 이전 Big O 수업과도 연결된다. 느슨한 상한이 참일 수 있듯, 느슨한 하한도 참일 수 있다. 최적성이라고 말하려면 같은 문제·같은 모델·같은 조건의 상한과 하한이 만나야 한다.

### C11. 31:55~36:47 RAM 모델과 정수 정렬의 전제

하한 설명을 마친 강사는 비교 모델을 벗어난다. Random Access Machine에서는 메모리를 배열처럼 보고 한 위치에 상수 시간으로 접근할 수 있다. 정수 key의 실제 값을 읽어 그에 해당하는 주소를 이용할 수 있으므로, 단순 비교가 주는 한 bit의 정보만으로 움직이는 모델보다 할 수 있는 일이 많다.

이제 입력 조건을 명시한다.

1. item은 n개다.
2. 정렬 기준인 key는 정수다.
3. 편의상 key는 `0, 1, ..., k-1` 범위에 있다. 가능한 key 값은 k개다.
4. 각 key는 machine word 하나에 들어간다.
5. 필요한 key 연산과 배열 접근을 상수 시간으로 수행하는 word-RAM 전제를 쓴다.

음수가 없다는 것은 편의를 위한 조건이라고 강사가 말한다. 그렇다고 이 강의에서 음수 처리 알고리즘을 자세히 수행한 것은 아니다. 사용자 퀴즈의 음수 범위 답변은 Part E에 별도로 보관한다. 정렬의 기준이 key라는 것도 중요하다. item에는 key 외의 정보가 있을 수 있고, 정렬 후에도 그 정보가 key와 함께 이동해야 한다.

word 조건은 계산 비용을 분석할 때 필요하다. 아주 긴 정수를 무조건 한 번의 기계 연산으로 처리할 수 있다고 가정하면 숨겨진 비용을 무시할 수 있다. 강사는 비교뿐 아니라 덧셈·뺄셈·곱셈·나눗셈 등의 연산도 이 모델에서 활용한다고 설명한다. 실제 언어의 무제한 길이 정수에 그대로 적용되는 보편적 비용 주장이 아니라 강의의 모델 가정이다.

35:49~36:34에는 일반적인 word 정수 정렬이 연구 주제라는 역사적 맥락이 나온다. 강사는 당시의 알고리즘으로 높은 확률에서 `n*sqrt(log log n)` 크기의 시간을 언급하고, 모든 경우 선형 정렬이 가능할 것이라는 추측도 말한다. 이는 **그 영상 시점의 발언**으로 보관하며, 2026년 현재의 최신 연구 결과나 확정된 정리로 단정하지 않는다. 해당 고급 알고리즘의 구현·증명은 이 강의 범위가 아니다. 이번에 실제로 배우는 것은 k가 적당한 경우의 Counting Sort와 Radix Sort다.

### C12. 36:47~39:35 Counting Sort의 빈도 예제

Counting Sort의 직관은 각 값이 몇 번 나오는지 세고 작은 key부터 그 개수만큼 출력하는 것이다. 강사가 말로 제시한 예제는 다음과 같다.

```text
입력: [3, 5, 7, 5, 5, 3, 6]

key      0  1  2  3  4  5  6  7
count    0  0  0  2  0  3  1  1

출력: [3, 3, 5, 5, 5, 6, 7]
```

원문에서는 뒤에 `whatever`를 덧붙이며 직관을 설명한다. 위 배열은 발화에 실제 나온 일곱 값을 놓은 것이며, 보이지 않는 추가 판서 값을 복원한 것은 아니다. key 범위가 0~7이라면 k=8개의 counter를 만든다. 각 item을 보면서 해당 key 위치의 counter를 1 증가시키고, 모든 입력을 처리한 뒤 counter 배열을 인덱스 순서대로 훑는다.

예를 들어 counter[3]=2라면 3을 두 번 출력하고, counter[5]=3이면 5를 세 번 출력한다. counter가 0인 위치에서는 출력할 것이 없지만 그 위치를 확인하는 비용은 든다. 따라서 작은 값부터 출력하기 위해 가능한 key 공간을 훑는 시간이 생긴다.

이 방법은 **정수 값만** 출력하면 맞지만, 강사는 이 버전을 최종 알고리즘으로 적지 않는다. item이 단순 정수가 아니라 추가 정보를 가진 객체이면 빈도만으로는 원래 객체를 구별해 되살릴 수 없기 때문이다. 몇 개가 있었는지 아는 것과 그 item 자체를 보존하는 것은 다르다. 다음 절의 리스트 방식은 이 문제를 해결한다.

### C13. 39:35~42:49 객체를 보존하는 리스트 방식

Spreadsheet에서 한 열을 기준으로 정렬하더라도 행의 나머지 열이 함께 이동해야 한다. key값만 정렬하고 나머지 데이터를 원래 위치에 놔두면 서로 다른 사람의 정보가 섞이는 것과 같다. 강사는 같은 key 3을 가진 객체 하나는 cloud, 다른 하나는 heart를 가진다고 설명한다. 두 개의 3이라는 개수만 기억하면 cloud와 heart의 객체가 사라진다.

해결은 각 key 위치에 counter 대신 **item 리스트**를 두는 것이다. 대본을 의사코드로 재구성하면 다음과 같다.

```text
CountingSortByKey(A, k, key):
    L = array of k empty lists
    for j = 0 .. n-1:
        r = key(A[j])
        append the whole item A[j] to L[r]

    output = empty list
    for r = 0 .. k-1:
        extend output with L[r], preserving list order
    return output
```

key(A[j])는 리스트를 선택하기 위한 정수이며, 저장하는 것은 A[j] 전체다. input 순서대로 같은 key의 리스트 끝에 붙이므로 같은 key끼리의 입력 순서도 남는다. key가 3인 cloud 객체가 먼저, heart 객체가 나중에 있었다면 L[3]에서도 그 순서를 유지한다.

```text
입력 순서
  (3, cloud) ... (3, heart)
       |             |
       +---- L[3] ---+
             [(3, cloud), (3, heart)]

key별 리스트를 작은 인덱스부터 연결
  L[0] + L[1] + ... + L[k-1]
```

이 도식의 cloud와 heart는 실제 그림을 복원한 것이 아니라 발화의 객체 구분을 문자열로 표시한 것이다. 리스트는 linked list나 Python list 등으로 생각할 수 있다고 강사가 말한다. 연결 리스트라면 끝 포인터를 이용해 append 비용을 상수로 유지해야 하며, 동적 배열 기반 리스트의 append는 보통 상각 O(1)이다. 이런 구현 비용 구분은 발화의 상수 append 전제를 해석한 보강 설명이다.

강사는 교재에는 리스트 대신 세 배열을 쓰는 다른 Counting Sort 구현이 있다고 명시한다. 이 교안은 지금 설명한 리스트 버전을 누적합·역순 배치 버전으로 바꿔 적지 않는다. 같은 알고리즘 이름이라도 저장 방식과 안정성을 확보하는 구현 논리가 다를 수 있으므로, 교수님 PDF의 구현은 그 자료 기준으로 따로 봐야 한다.

### C14. 42:49~44:23 Counting Sort 비용 분석

강사가 학생들에게 각 단계를 물으며 계산하는 비용은 다음과 같다.

| 단계 | 작업 수와 전제 | 비용 |
| --- | --- | --- |
| 리스트 배열 초기화 | 빈 리스트를 k개 생성 | O(k) |
| 입력 분배 | n개 item의 key를 읽고 해당 리스트에 append | O(n) |
| 출력 연결 | k개 리스트를 확인하고 저장된 item 전부 출력 | O(n+k) |
| 합계 | 초기화·분배·출력을 모두 포함 | O(n+k) |

초기화 단계에서 학생은 n 또는 상수를 답하지만, 강사는 k라고 바로잡는다. item 수만 보면 안 되고 key별로 준비하는 슬롯 수를 봐야 한다. 입력 분배는 key를 상수 시간에 계산하고 append를 상수 또는 상각 상수로 처리한다는 전제 아래 n번이다.

출력 연결은 리스트마다 길이가 다르더라도 전체 원소 수의 합이 n이라는 사실을 쓴다. n개 item은 각각 하나의 리스트에 한 번 들어간다. 빈 리스트 확인 비용도 있으므로 다음 식이다.

```text
sum(r=0..k-1) (|L[r]| + 1)
  = sum(r=0..k-1) |L[r]| + k
  = n + k
```

각 리스트의 길이를 n으로 놓고 k번 반복하니 nk라고 계산하는 것은 이 구조에서 지나친 계산이다. 리스트들은 서로 같은 n개 원소를 복사해 가진 것이 아니라 n개 원소를 나누어 가진다. 구현이 모든 버킷마다 입력 전체를 다시 훑는 방식이면 별도 분석이 필요하지만 그것은 위 알고리즘과 다르다.

따라서 k=O(n)이면 시간은 O(n)이다. k가 매우 크면 실제 입력이 적어도 key 공간 초기화·순회가 오래 걸린다. 리스트 슬롯과 item 저장, 출력 배열을 세면 추가 공간도 O(n+k)이며, 이 공간 식은 의사코드 구조를 바탕으로 덧붙인 분석이다. k를 줄이기 위해 key가 가지는 자리 정보를 이용하는 다음 Radix Sort로 넘어간다.

### C15. 44:31~48:33 Radix Sort의 자릿수와 처리 순서

Radix Sort는 Counting Sort를 버리지 않고 **작은 key 범위의 부분 정렬을 반복하는 subroutine**으로 쓴다. 전체 정수 값은 커도 한 자리의 가능한 숫자는 적을 수 있다는 점을 이용한다. 강사는 key가 `n^100`까지 커져도 선형 시간이 가능한 조건을 목표로 제시한다. 이때 100은 n과 함께 늘어나는 값이 아니라 고정 상수로 생각한다.

정수를 base b로 표현하면 각 digit은 0~b-1이다. 보통 쓰는 10진법이나 컴퓨터의 2진법으로 고정할 필요가 없다. 같은 정수라도 선택한 b에 따라 자릿수가 달라진다. 더 큰 b는 digit 수를 줄이지만 Counting Sort가 관리할 슬롯 수를 늘린다.

```text
K = a[d-1]*b^(d-1) + ... + a[1]*b + a[0]
각 a[j]는 0 <= a[j] < b
```

key 범위가 `0 <= K < k`라면 모든 key에 필요한 자릿수를 공통으로 `d=max(1, ceil(log_b k))`로 잡을 수 있다. k=1도 적어도 한 자리로 표시하며, b>=2라고 가정한다. 최대값을 k라고 포괄적으로 부르는 대본의 표현에서는 `floor(log_b k)+1` 형태도 나온다. 최대값이 k인지 k-1인지와 끝점 차이를 구분하되, 비용 분석의 핵심은 `d=O(1+log_b k)`다.

실행 순서는 **least significant digit부터 most significant digit까지**다.

```text
ones digit 역할의 a[0]으로 stable Counting Sort
  -> a[1]으로 stable Counting Sort
  -> ...
  -> 가장 높은 a[d-1]로 stable Counting Sort
```

매번 digit 값 하나를 key로 써서 **전체 item을** 정렬한다. 숫자의 일부 자리만 출력하거나 원래 숫자를 그 자리 숫자로 덮어쓰는 것이 아니다. 강사의 Spreadsheet 비유도 우선순위가 낮은 열을 먼저 정렬하고 높은 열을 나중에 정렬하는 것이다. 낮은 우선순위 열로 만들어 놓은 동률 내부 순서를 높은 열 정렬이 보존해야 여러 열의 기준이 결합된다.

강사는 시간이 부족해 이 강의에서는 자세한 숫자별 Radix 예제를 진행하지 못하고 교재·노트의 예제를 참고하라고 말한다. Part B의 base-5 예제나 Part E의 `[32,03,44,42,22]`를 이 영상에서 실제 수행한 예제로 바꾸어 기록하지 않는다. 여기서는 이 영상의 설명과 비용 분석을 유지하고, 구체적 배열 연습은 해당 출처의 절로 연결한다.

### C16. 48:33~49:57 자릿수 추출과 한 패스의 비용

Counting Sort의 일반 비용은 O(n+k)였다. 하지만 지금은 원래 정수 전체를 key로 쓰는 것이 아니다. 정수의 특정 자릿수를 key로 쓰므로 가능한 값은 0~b-1이고 범위 크기는 b다. 따라서 **한 패스**의 비용은 O(n+b)다.

```text
전체 정수의 범위: 0..k-1
한 자리 숫자의 범위: 0..b-1

Counting Sort 슬롯 수 = k가 아니라 b
```

낮은 자리 숫자는 `K mod b`로 얻고, j번째 자리는 다음과 같이 계산한다.

```text
digit_j(K) = floor(K / b^j) mod b
```

강사의 설명은 현재 필요한 digit을 나눗셈과 나머지 연산이라는 상수 개수의 연산으로 얻을 수 있다는 것이다. key가 word에 들어가고 해당 연산이 상수 시간이라는 가정을 여기서 다시 쓴다. b^j는 현재 패스에서 사용하는 자리 가중치로 준비해 두면 item마다 지수를 반복 계산할 필요가 없다. 가중치 관리와 마지막 자리의 overflow를 피하는 것은 실제 구현에서 신경 써야 할 사항이지, 긴 정수 연산을 무조건 무료로 허용하는 것은 아니다.

모든 정수를 처음부터 자릿수 문자열이나 배열로 변환해 둘 필요는 없다. 현재 패스가 보는 자리만 계산하면 된다. 강사는 먼저 미리 자릿수를 모두 써 놓는 비용을 걱정하고, 49:44에는 미리 계산해 둘 수도 있다고 덧붙인다. 어느 쪽이든 중요한 것은 **처리하는 자리 수와 그 준비 비용을 숨기지 않는 것**이다. 이 강의의 선형 조건 아래서는 총 자리 수도 상수 배의 n이다.

총 d번 반복하므로 전체 비용은 다음과 같다.

```text
T(n,k,b) = O((n+b)*d)
         = O((n+b)*max(1, ceil(log_b k)))
```

d를 따로 쓰면 k와 b의 변화가 명확하다. b가 커져 패스 수가 작아져도, 각 패스에서 b개 슬롯을 처리해야 한다. 반대로 b를 2처럼 작게 고정하면 패스는 싸지만 큰 key를 다루기 위해 더 많은 패스가 필요하다.

### C17. 49:57~52:05 밑 선택과 선형 시간 조건

강사는 `O((n+b)*d)`를 적은 뒤 b를 어떻게 정할지 묻는다. 큰 b는 로그의 밑을 키워 digit 수를 줄이지만, 너무 큰 b는 n+b에서 슬롯 비용을 크게 만든다. 학생이 n을 제안하고 강사는 좋은 선택이라고 답한다. n>=2에서 b=n으로 잡으면 한 패스 비용은 O(2n)=O(n)이다.

key 공간이 고정 상수 c에 대해 `k <= n^c`라면 다음 관계가 성립한다.

```text
log_n k <= c
d = max(1, ceil(log_n k)) = O(1)

T = O((n+n)*d) = O(n)
```

그래서 값 자체가 n의 다항식으로 제한되는 정수는 이 전제에서 선형 시간에 정렬할 수 있다. `n^100`처럼 값이 커 보이더라도 자릿수를 base n으로 세면 상수 개의 패스다. 최대값을 `n^100`까지 포함한다고 표현하면 끝점 때문에 한 자리가 더 필요할 수 있지만, 상수 패스라는 결론은 같다. 일반적인 식에서는 최소 한 패스 비용도 포함하여 `O(n*(1+log_n k))`라고 쓰면 작은 k에서의 표현도 안전하다.

여기서 c가 고정이라는 조건은 빠지면 안 된다. key 범위가 n에 대해 지수적으로 늘어나면 log_n k도 상수가 아닐 수 있다. 예를 들어 k=2^n이면 log_n k=n/log2 n이므로 같은 설정에서 자리 수가 계속 늘어난다. 이 예시는 조건을 설명하기 위해 교안에서 덧붙인 것으로 영상에서 계산한 예제가 아니다. 또한 n=0,1은 정렬할 일이 없거나 원소 하나만 있으므로 따로 처리하면 된다. base 1을 설정해 일반 자릿수 정렬을 하지는 않는다.

51:05~51:18에 강사는 미분으로 최적화할 수 있고 b=Theta(n)이라고 거칠게 설명한다. 이 교안에서는 이를 **다항 범위에서 선형 시간을 얻기에 충분한 선택**으로 사용한다. 모든 n,k에 대해 b=n이 정확한 수치적 최소라고 증명한 것으로 확대하지 않는다. 정수 밑·자릿수 반올림을 포함한 최적화와 이번 강의의 O(n) 달성은 별개다.

두 번의 정정도 중요하다. 50:03에 digit 수의 로그에 n을 적었다가 50:28에 k라고 고친다. 51:26의 다항 범위 설명도 51:36에서 `k <= n^c`로 명확히 적는다. 최종 분석에 사용하는 로그의 대상은 입력 수 n이 아니라 key 공간 k다.

### C18. 안정성과 귀납법으로 연결한 정확성

대본의 마지막 문장은 간단한 induction으로 증명할 수 있다는 안내이며, 긴 증명을 실제 수행하지는 않는다. 아래는 **강의의 리스트 방식과 자리 순서를 바탕으로 교안에서 풀어 쓴 보강 증명**이다. 영상에서 이 문장들을 그대로 말했다고 취급하지 않는다.

먼저 Counting Sort는 key의 순서와 item 보존을 모두 만족한다. 각 입력 item을 자신의 key 리스트에 정확히 한 번 저장하고, 리스트를 key 인덱스 순서대로 출력하므로 모든 item이 한 번씩 출력된다. 앞 리스트의 key는 뒤 리스트의 key보다 작다. 같은 key의 item은 입력 순서대로 리스트 끝에 append되어 같은 순서로 출력된다. 따라서 item의 permutation을 유지하며 key에 대해 오름차순이고 stable하다.

Radix Sort는 j개 패스를 끝냈을 때 item들이 **낮은 j자리로 이루어진 값에 대해 정렬되어 있다**는 불변식으로 본다. 앞에 없는 높은 자리는 0으로 생각해 모든 item의 자리 수를 맞출 수 있다.

| 단계 | 귀납적 설명 |
| --- | --- |
| 첫 패스 | 가장 낮은 a[0] 하나를 정렬했으므로 낮은 한 자리에 대해 정렬됨 |
| 귀납 가정 | 낮은 j자리의 순서는 이미 올바름 |
| 다음 패스 | a[j]로 stable하게 정렬하여 서로 다른 a[j]를 올바른 순서에 배치 |
| 같은 a[j]인 경우 | 안정성이 낮은 j자리의 기존 순서를 유지 |
| 패스 뒤 | a[j]와 낮은 j자리를 합친 j+1자리 전체의 순서가 올바름 |
| 종료 | 모든 d자리를 처리했으므로 원래 정수 전체에 대해 정렬됨 |

왜 stable이어야 하는가도 여기서 드러난다. 다음 패스에서 높은 자리 값이 같은 두 item의 순서를 뒤집으면 이미 만들어 둔 낮은 자리의 순서가 깨질 수 있다. 리스트 Counting Sort는 입력 순서를 보존하므로 이 조건을 충족한다. 높은 자리부터 아무 그룹 구분 없이 전체 배열을 반복 정렬하는 방식과 혼동하지 않는다.

각 패스는 item을 버리거나 새 item으로 바꾸는 것이 아니라 위치만 바꾸는 permutation이다. 따라서 마지막에도 원래 n개 item과 payload가 보존된다. 정확성은 숫자가 오름차순인 것만이 아니라 원래 item이 남아 있다는 조건까지 포함한다. 강의의 cloud/heart 예제가 뒤의 자릿수 정렬에도 필요한 이유다.

### E01. Direct Access Array Sort의 선형 시간 조건

#### 문제 원문

Explain what conditions are needed to achieve the linear time for direct access array sort.

#### 사용자 답변 원문

> 1. Explain what conditions are needed to achieve linear time for direct access array sort.
> To achieve linear time, all keys must be unique integers. Also, the key range u must be O(n), where n is the number of items. We store each item at the array index equal to its key. Then we scan the array in order. The total running time is O(n + u), which becomes O(n) when u = O(n).

### E02. Tuple Sort의 단계별 과정

#### 문제 원문

Show how tuple sort works on [32, 03, 44, 42, 22].

#### 사용자 답변 원문

> 2. Show how tuple sort works on [32, 03, 44, 42, 22].
> We use stable sorting from the least significant digit to the most significant digit.
> Original: [32, 03, 44, 42, 22]
> First, sort by the last digit: [32, 42, 22, 03, 44]
> Next, sort by the first digit: [03, 22, 32, 42, 44]
> This is the final sorted order. We need a stable sort to keep the correct order of items with the same digit.

### E03. Counting Sort의 단점과 해결 방법

#### 문제 원문

What is the drawback of counting sort? How can we address the drawback?

#### 사용자 답변 원문

> 3. What is the drawback of counting sort? How can we address the drawback?
> The main drawback is that counting sort needs a large array when the key range u is large. Its time and space complexity are O(n + u). We can solve this problem by using radix sort. Radix sort splits large numbers into smaller digits and uses stable counting sort on each digit. This can give O(n) time when the key range is polynomial in n.

### E04. 음수가 포함된 범위의 선형 정렬

#### 문제 원문

Describe a linear time algorithm to sort n integers from the range [-n^3, …, n].

#### 사용자 답변 원문

> 4. Describe a linear time algorithm to sort n integers from the range [-n³, …, n].
> First, add n³ to every number to make all numbers non-negative. Now the numbers are between 0 and n³ + n.
> Next, represent each number in base n. For n ≥ 2, each number needs at most four digits. Use radix sort with stable counting sort, starting from the least significant digit. Each pass takes O(n) time because each digit has only n possible values.
> After four passes, subtract n³ from every number to get the original values. The numbers are now sorted.
> The total running time is O(4n) = O(n).
